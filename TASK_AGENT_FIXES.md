## R15.5 — чек-лист для пользователя

Закрывается только живым прогоном, агент его сам не закроет.

1. Сделать в приложении задачу с большим объёмом `bash`/`read_many` (20+ шагов) и
   повторить её дважды: сначала с `Tuning.toolOutputPruning = .off`, затем с `.budget`.
2. Прислать из `~/HARNES_S_DATA/logs/latency.log` по каждой сессии:
   - строки `prompt_breakdown` (`phase=pre_prune` и обычную) на одном и том же шаге;
   - соответствующую строку `cache_hit=… prompt_tokens=…`;
   - строку `pruned tool_results=… saved_tokens=…`, если была.
3. Критерий R15.5: `total_est` (после прунинга) и `prompt_tokens` того же запроса
   расходятся меньше чем на 10% — отдельно для запроса с картинками и без.
4. Критерий приёмки прунинга: `prompt_tokens` на сопоставимом шаге падает не меньше
   чем на 30% при том же числе шагов.

Числа вносятся сюда таблицей; до этого пункт остаётся открытым, даже если все тесты
зелёные.

## R16.6 — что осталось

Сделано и закрыто: гварды системных вкладок и ладдер `webfetch` → `browser`
(`621922a`, `BrowserGuardInterceptor`, тесты `BrowserGuardTests`).

Не сделано:

- **Профиль Chrome по CDP** — подключение к Chrome, поднятому пользователем с
  `--remote-debugging-port` и отдельным `--user-data-dir`, для работы на залогиненных
  сайтах без хранения паролей в приложении.
- **Сохранение состояния сессии** — прогон `browser_save_state` / `browser_load_state`,
  чтобы логин пережил перезапуск.
- **`browser_list`** — открытые сессии, URL, жива ли сессия.

Все три требуют постоянного процесса-сессии: `browser` сейчас запускает одноразовый
`node` + Playwright на каждый вызов. Ни один из критериев нельзя закрыть тестом в этом
репозитории — только ручным прогоном с поднятым Chrome. Поэтому либо ручная приёмка,
либо вынос в отдельную задачу с живым окружением.

## Отложено по замеру

Не брать без нового замера, показывающего, что оно того стоит.

- **R11.4, предвыгрузка саммари.** Суммаризация заранее при ~60k до потолка, результат
  лежит неприменённый. Нужен кэш чекпойнта с инвалидацией по границе покрытых сообщений.
  Дорого по токенам, выигрыш только на сессиях, доходящих до потолка.
- **ANN-индекс.** Точный перебор: резидентная матрица до 40 000 векторов + `cblas_sgemv`
  (10k — 1,5 мс, 40k — 5,5 мс), выше `vDSP` построчно (14,6 / 59 мс). Точка врезки —
  `streamedMatches`, не `bestMatches`. HNSW/IVF — при стабильных 100–200 тыс. чанков или
  p95 > 100 мс.
- **R6, бюджет схем.** 51 инструмент = 5 187 токенов из 5 600 (`Tuning.schemaTokenBudget`),
  запас делят MCP-инструменты. Порядок при переполнении: укоротить описания →
  deferred-каталог редких групп → профили по режимам (ломают кэш префикса) → осознанно
  поднять потолок с записью замера.
- **Политика `allow / ask / deny`.** `ask` требует диалога из середины цикла: continuation
  в execute, событие в `AgentLoop.Event`, шит в UI.
- **Checkpoint хода.** `file_versions.turn_id`, `restoreTurn(id)`, `/undo-turn`.
- **`session_search`, hooks, песочница, параллельные подагенты.** Параллельным
  подагентам сначала нужен worktree на каждого писателя.

## Чего делать нельзя

- **Не трогать промпт попутно.** `Core/Agent/Prompts.swift`, `ToolDefinitions.swift` —
  только если пункт задания прямо просит.
- **Не менять данные приложения.** `~/HARNES_S_DATA/` — живые база, память, журналы.
  Читать можно, писать — только кодом приложения при обычной работе.
- **Не удалять логи и бэкапы.** `latency.log` — единственный источник замеров.
- **Не поднимать чужие процессы.** Модели, серверы, MCP поднимает пользователь.
- **Не отчитываться без чисел.** «Стало лучше» — не отчёт. Отчёт — строка журнала или
  таблица.
- **Не возвращать Windows-порт.** `4aac748` удалил `WINDOWS_PORT.md`,
  `App/ContractExporter.swift` и `Scripts/seed_windows_repo.sh`. Порта не будет никогда.
- **Не выдумывать сигнатуры API.** Сверяйся с исходниками или MCP-сервером проекта; если
  справки под рукой нет — скажи прямо, а не пиши по памяти.
