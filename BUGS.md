## B1 — граница саммари в `chat_state` разъехалась с реальной историей

**Severity:** высокая (тихая потеря контекста, не видна в UI).

**Симптом.** Чат работает, ответы идут, но всё, что было раньше, живёт только
в саммари. Модель не видит историю, хотя в базе она есть.

**Факты с машины:**

```
sqlite3 ~/HARNES_S_DATA/database/harness.db "select * from chat_state;"
1|10151|2026-11-19T07:25:30Z

sqlite3 harness.db "select count(*), min(id), max(id) from messages;"
18566|3|18568
```

`summarized_up_to = 10151`, последнее сообщение `18568`. За границей —
8424 сообщения, из них 706 сообщений пользователя. При этом
`summary=9460` токенов в `prompt_breakdown` не меняется с 21:24 18.11 —
новых сжатий после последнего чекпойнта не было.

**Причина.** В `Models/ChatStore+Compaction.swift` в чекпойнт пишутся
оба поля одним и тем же значением:

```swift
try? await services.compaction.saveCheckpoint(
    CompactionService.Checkpoint(
        summary: summary,
        coveredMessageCount: checkpointCovered,
        createdAt: Timestamps.now(),
        summarizedUpTo: checkpointCovered   // <-- счётчик, не id
    ),
    database: services.database
)
```

`checkpointCovered` — это **количество свёрнутых сообщений**, а не id
последнего свёрнутого сообщения. Настоящий id лежит рядом, в
`compactedThroughID` (строка 254: `compactedThroughID = messages[lastCompacted.id].id`).
Две системы координат смешаны в одном поле.

После перезапуска приложения `checkpointCovered` восстанавливается из
чекпойнта, а `summarizedUpTo` читается как позиция в истории. Как только
эти числа расходятся (перезапуск, ручной `/compact`, сброс счётчика),
граница уезжает вперёд и перестаёт что-либо означать.

**Что делать.**

1. Развести поля: `summarizedUpTo` — всегда id последнего свёрнутого
   сообщения (`compactedThroughID`), `coveredMessageCount` — счётчик для
   статистики и для `retainedUserMessages`.
2. Миграция GRDB (только добавляющая, по правилу R30): переложить
   существующее значение `summarized_up_to` в `covered_message_count`,
   а `summarized_up_to` пересчитать из `compactedThroughID` чекпойнта.
   Если чекпойнта нет — обнулить и позволить одному полному сжатию.
3. Тест: сжать, перезапустить, сжать ещё раз — `summarized_up_to`
   обязан монотонно расти по id и никогда не превышать `max(messages.id)`.

**Проверка после фикса:**

```
sqlite3 harness.db "select summarized_up_to from chat_state;"
sqlite3 harness.db "select max(id) from messages;"
-- первое должно быть <= второго и совпадать с реальной границей саммари
```

## B2 — сжатие ничего не пишет в `latency.log`

**Severity:** средняя (баг не диагностируется, приёмка невозможна).

**Симптом.** После трёх сжатий в `latency.log` нет ни одной записи о них.

**Факты:**

```
grep -c "compaction" ~/HARNES_S_DATA/logs/latency.log
```

На всё время работы — ровно две строки, обе от 11.11:

```
2026-11-11T04:03:06Z window 800000 -> 245000: preflight compaction
2026-11-11T07:19:05Z window 800000 -> 245000: preflight compaction
```

По сжатиям 18–19.11 нет ни успеха, ни провала, ни страйков.

**Причина.** `recordCompactionEffectiveness(before:services:)`
(`ChatStore+Compaction.swift:451`) обновляет `CompactionGuard` и
сохраняет его, но сам ничего не логирует. `Self.logLatency` вызывается
только в ветке ошибки (строка 283: `compaction failed (Nx)`). Успешное
сжатие и блокировка по страйкам молчат.

**Что делать.** Три строки в `logLatency`:
- успех: `compaction ok messages=N summary_tokens=A->B` — до/после
  саммари и сколько сообщений свёрнуто;
- провал: уже есть, оставить;
- блок по страйкам (строка 358): сейчас пишется только
  `compaction blocked by strikes until ...` — добавить счётчик страйков.

**Проверка после фикса:** прогнать `/compact`, найти в логе строку
`compaction ok` с реальными числами.

## B3 — пустые assistant-записи идут в саммаризацию

**Severity:** средняя (лишние токены, размытое саммари, мусор в статистике).

**Симптом.** Больше половины сообщений в базе — assistant с пустым текстом.

**Факты:**

```
-- до границы саммари
select count(*) from messages where id<10151 and role='assistant' and length(text)=0;
5110            -- из 10148 всего

-- после границы
select count(*) from messages where id>10151 and role='assistant' and length(text)=0;
6231            -- из 8424 всего
```

Пустые записи попадают в `prompt_breakdown` как сообщения
(`messages=90`) и, судя по `compact(plan.compacted, ...)`, идут в
`contextMessages` для `summarize`.

**Что делать.**

1. При формировании саммари отфильтровать `role == "assistant" && text.isEmpty`
   до вызова `services.compaction.summarize` — они не несут смысла.
2. В `contextPlan` считать токены только по записям с непустым текстом,
   иначе оценка объёма истории завышена, а оставшийся бюджет — занижен.
3. Не удалять их из базы: `contexts`/`exchanges` могут на них ссылаться
   по id. Только исключать из подачи модели.

**Проверка после фикса:** `messages=` в `prompt_breakdown` должен упасть
кратно, при этом `history=` — остаться прежним по смыслу.

## B4 — чат «сжимается» без записи чекпойнта

**Severity:** средняя (пользователю показывают действие, которого не было).

**Симптом.** Пользователь видел три сжатия, в логе и базе — одно.

**Факты.** Последняя запись `chat_state.updated_at = 2026-11-19T07:25:30Z`,
`summary` с тех пор не менялся. `summary_tokens` в `prompt_breakdown`
в 21:24, 07:00, 07:23 и 07:26 — одно и то же число 9460.

**Вероятные причины (требует подтверждения после B2):**

1. Срабатывает прунинг вывода инструментов (`pre_prune`), а не сжатие —
   `total_est` падает (98585 → 53937), но `summary` не трогается. Тогда
   это не баг, а уведомление: пользователю пишут «История сжата», хотя
   сработал прунинг.
2. Сжатие упало, но `notice` не показал провал из-за ветки
   `if compactionCoolingDown { return }` (строка 354) — молчаливый выход
   без уведомления.

**Что делать.** Сначала закрыть B2 и получить реальные строки в логе.
Затем развести в UI два разных события: «вывод инструментов обрезан» и
«история свёрнута в саммари». Сейчас оба пути ведут к похожему ощущению,
а сообщение говорит только про второе. Ветку `compactionCoolingDown`
снабдить хотя бы тихим логом — сейчас не остаётся следов.

## B5 — память заполняется мусором при сжатии

**Severity:** высокая (портит доверие к памяти целиком).

**Факт.** Записи с `source='compaction'` — 25 из 90. Из них больше половины
бесполезны, часть прямо вредна:

```
id | content (начало)
111 | Пользователь имеет Apple Developer Account, приложение подписано этим аккаунтом вчера.
112 | Пользователь также получил что-то из Apple ID вчера.
106 | У пользователя есть токен от GitHub, который он передал ассистенту
 85 | У пользователя есть проект Mecha с сайтом https://bazarow.ru/tools/meha/ и страничкой вендинга.
 92 | У пользователя есть проект Mecha, его сайт — https://bazarow.ru/tools/meha/, скачать можно только...
 98 | У пользователя есть проект «Меха» (Mecha) — инструмент, который можно скачать только с его сайта...
 99 | Сайт пользователя — bazarow.ru, страница про Меху: https://bazarow.ru/tools/meha/
 97 | Пользователь работает над проектом «Килокод» (KiloCode / kilocode), которому можно поручать задачи
```

**Что не так.**

1. `111` и `112` — пересказ реплики из середины диалога словами «вчера» и
   «что-то». Второе вообще не факт, это оговорка. Оба сейчас лежат в промпте
   как `fact` с `importance = 1`.
2. `85`, `92`, `98`, `99` — один и тот же факт про сайт Мехи, записанный
   четырежды разными словами. `content_hash` их не ловит: хэш от полного
   текста, а тексты разные.
3. `106` дублирует `105` («токен лежит в `~/.git-credentials-harness`»):
   `105` точная и полезная, `106` — её испорченная тень.
4. `83` («Срок действия сертификата — до 19.10.2027») была неправдой два
   месяца и жила в промпте, пока не поправили руками.

**Причина.** Сжатие извлекает факты промптом-экстрактором и пишет всё, что
похоже на утверждение, без проверки: есть ли уже такой факт, есть ли в нём
дата/число/путь, и не является ли текст пересказом пересказа.

**Что делать.**

- В экстракторе сжатия запретить формулировки с «вчера», «сегодня», «что-то»,
  «возможно», «наверное», «кажется» — они не привязаны ко времени и станут
  ложью через сутки.
- Перед записью искать похожие по эмбеддингу (таблица `embeddings` уже есть,
  90 векторов, все актуальны) и при косинусе выше порога обновлять
  существующую запись, а не плодить новую.
- Факты без даты, числа или пути считать слабыми: писать с `importance = 0`,
  в промпт не пускать.

**Проверка.**

```
sqlite3 ~/HARNES_S_DATA/database/harness.db \
  "select count(*) from memory where source='compaction' and content like '%вчера%' or content like '%что-то%';"
```

Сейчас — 2. После правки — 0 и не растёт.

## B6 — в памяти лежат записи, которые никогда не читались

**Severity:** средняя (балласт в бюджете промпта).

**Факт.** 22 записи из 90 имеют `hits = 0`, то есть за всё время ни разу не

`Tuning.memoryPromptBudgetTokens = 3_000` (`Core/Agent/Tuning.swift:36`).
Значит факты **не влезают в бюджет**: `fact` идёт последним в приоритете
(`MemoryService.swift:282`), и хвост отбрасывается молча — считается в
`omitted`, но не показывается.

**Что это значит на практике.** Записи `62`, `65`, `70`, `71`, `72`, `75` —
все замеры LLMSERVER, Gemma, Strata, `llm.sh`. Полезные, но ни разу не
прочитанные: они не влезли ни в один промпт. То же с `108`, `109` — факты про
сертификат и нотаризацию, добавленные сегодня, — уже `hits = 0`.

**Что делать.**

- `memory_stats` (уже запрошен как R34.2) должен показывать `omitted` по
  областям: сколько фактов выброшено из-за бюджета за последний ход.
- Разделить бюджет: закреплённое и `lessons` — всегда, остальное — по
  релевантности к текущему запросу, а не по `id`. Сейчас `id` вторым
  критерием, поэтому свежие записи вытесняют старые независимо от смысла.
- Записи с `hits = 0` старше 30 дней — кандидаты на `importance = 0`
  (не удаление, а «не пускать в промпт»).

**Проверка.**

```
sqlite3 harness.db "select area, round(sum(length(content))/3.0) tok from memory group by area;"
```

После правки сумма по областям кроме `lessons` должна быть ≤ 3000, либо
`omitted` должно быть видно в логе.

## С чего начинать

**Первый коммит — B2 (логирование сжатия).** Не B1, не миграция. Причина простая:
сейчас из `latency.log` не видно ни одного сжатия, кроме двух строк от 11 ноября.

сам, глядя в лог, — поэтому он первый.

**Второй — B9 (видимость памяти в логе).** Тот же аргумент: без `memory=` и
`memory_tok=` в `prompt_breakdown` невозможно замерить B6 («22 записи никогда не

**Третий — B1 (граница саммари).** Только миграция, только добавляющая. Плюс
тест: сжать → перезапустить приложение → сжать снова, граница не должна уехать.

**Четвёртый — B3 (пустые assistant-записи).** Фильтровать при подаче модели,

**Пятый — B5 (мусор в памяти).** Это чистка руками, а не код: убери

B4 проверяется последним, потому что его нельзя доказать без B2.

## Как считать пункт закрытым

- **Только живым запуском.** Тест зелёный — не доказательство. Пункт про логи
  закрыт, когда в `~/HARNES_S_DATA/logs/latency.log` появилась строка, которую
  там раньше не печатали, и Kilo её показал.
- **Пункт про базу** закрыт, когда приложена команда `sqlite3` и её вывод
  до/после. Не «поправил», а «было `10151`, стало `18568`».
- **Не выдавать сделанное за проверенное.** Если проверка требует твоего телефона,
  TCC-диалога или живой сессии — писать «живым запуском не проверено» жирным
  в отчёте, а не закрывать пункт.
- **Регрессия важнее фичи.** Если правка ради B1 сломала сжатие на пустой
  истории — откат, а не «доделаю потом».

## Чего не делать

- **Миграции только добавляющие.** Новая колонка или новая таблица — да.
  Переименовать, поменять тип, удалить колонку — нет. Формат данных на диске
  не меняется (правило R30).
- **Из базы ничего не удалять.** B3 чинится фильтром на чтении, а не `DELETE`.
  Сжатие отвязывает историю от промпта — оно её не стирает. Это архитектурное
  свойство, а не случайность: на него завязано восстановление после провала.
- **Не трогать `bitrix/`** и не править вендорные зависимости.
- **Не переписывать `AGENTS.md`, `AGENT_PROCESS.md`** и не заводить S/M/L, часы
  и рубли в оценках.
- **Не править `project.yml` и `CODE_SIGN_IDENTITY`.** Release-сборка и
  нотаризация — отдельная процедура, не часть этих багов.
- **Не пушить.** Коммит по слову пользователя, push по слову пользователя.
- **Не писать новые файлы с задачами.** Всё новое, что нашёл по дороге,
  дописывается сюда, в `BUGS.md`, новым номером с severity и командой проверки.
  `TASK_AGENT_FIXES.md` удаляется и не восстанавливается.

# Забрать у Оборбота (LM-сервер, /opt/oborbot)

Проверено на живой машине 19.11.2026. Оборбот — Rust, память Graph RAG,
~10 000 узлов, работает 24/7 с сентября. Источники: `README.md` раздел 2.13,
`crates/core/src/memory/{search,entities,mod}.rs`, `tools/rag_bench.py`.

**Забираем не архитектуру, а три готовых решения.** Целиком Graph RAG тянуть
не надо: у нас GRDB и один пользователь, у него 10 000 событий чата стрима.
Но три вещи у него сделаны и проверены на реальных данных, и у нас их нет.

## B11 — фильтр шлака перед записью памяти

Прямое лекарство от B5. У нас в память пишется всё, включая «Пользователь также
получил что-то из Apple ID вчера».

У него — две функции, обе дешёвые и без LLM:

**`is_low_value(text, source)`** (`memory/mod.rs:312`) — на входе события:
- меньше 3 букв (эмодзи, «+», «++») — мимо;
- точное совпадение со словарём-мусором: «ку», «ок», «ага», «спс», «норм»,
  «ахаха», «лол», «кек», «это», «вот», «да», «нет» — мимо;
- порог по источнику: youtube < 6 букв, telegram < 4, остальное пропускаем.

**`is_junk_fact(fact)`** (`memory/entities.rs:186`) — на входе факта:
- короче 8 символов — мимо;
- 12 префиксов-пересказов: «говорящ…», «упомянут…», «автор сообщения»,
  «пользователь,», «зритель,», «участник чата», «написал сообщение» — мимо;
- хвосты «…, упомянутый/упомянутая/упомянутое говорящим» — мимо.

Второй список — ровно то, что нам нужно. Это отвергает «Пользователь также
получил…» до записи, а не после чистки руками.

**Что делать у нас.** Портировать оба списка в `MemoryService` как guard в
`add()`. Плюс `source`: у нас источники — `agent`, `compaction`, `user`.
Для `compaction` порог строже, потому что именно оттуда идёт шлак.
Тест: запись «Пользователь также получил что-то из Apple ID» должна вернуть
отказ, а не создать строку.

## B12 — гибридный поиск 0.65/0.35 у нас есть, а рецепт ранжирования — нет

`search.rs:110-144`. Формула, проверенная на 10 000 событий:

```
base      = cos * 0.65 + lex * 0.35     // вектор + лексика (BM25-lite)
recency   = 1.0 если «вопрос о прошлом», иначе 0.985^дней
frequency = 1.0 + 0.1 * access_count
importance= source_multiplier(source)
centrality= 1.0 + degree_centrality * 0.3
score     = base * recency * frequency * importance * centrality
```

Три вещи здесь стоят заимствования:

**1. Вопрос о прошлом отключает штраф за давность.** Если в запросе есть
«давно», «помниш…», «раньше», «когда», «истори…», «было» — `recency = 1.0`.
Логично до безобразия: зачем штрафовать за старость, если спрашивают именно
про старое. У нас `MemoryRanker` штрафует всех одинаково.

**2. `0.985^дней` вместо `0.9^дней`.** У него это было исправлением: `0.9`
убивал память за месяц. `0.985` — половина веса за ~46 дней. Для ассистента,
который живёт годами, это правильнее.

**3. `access_count` в формуле.** Каждое чтение поднимает вес факта
(`increment_access_counts` после каждого поиска). Читаемое всплывает,
нечитаемое тонет само. Это лекарство от нашего B6 без ручной чистки.

**Отдельно — fallback при пустом результате** (`search.rs:145-162`): если
ничего не нашли, отдать свежие события за 48 часов. Не пустоту. У нас
`memory_search` на промахе возвращает пусто, и я не иду дальше.

## B13 — RAG-бенчмарк: recall@1 88%, recall@5 98%

`tools/rag_bench.py`, 130 строк Python. Как устроен:

1. Берёт случайные события из памяти (`random.seed(42)` — воспроизводимо).
2. Делает из текста события «вопрос» (первые 300 символов).
3. Ищет по эмбеддингам, смотрит, попало ли исходное событие в топ-1 и топ-5.
4. Мусор короче 15 букв отфильтровывается перед выборкой.

У него этот скрипт **привёл к числам** все улучшения RAG: до него улучшения
делались на глазок. У нас нет ни одного замера качества памяти — я не могу
сказать, находит ли `memory_search` то, что должен. Это дороже любых
улучшений: без метрики любая оптимизация памяти — вера.

**Что делать у нас.** Свой вариант: случайные записи `memory` → их `text` →
`memory_search` → доля попаданий в топ-1/топ-5. Тест в `Tests/`, чтобы
падал при регрессии. Сначала замерить «как есть», потом трогать B6/B7.

## Оборбот: что не брать

- **Graph RAG с 10 000 узлов.** Оправдан для стрима с толпой зрителей.
  У нас один пользователь — граф ради графа (у нас уже 10 связей на 90
  записей и он пуст).
- **Мнения и личность** (`opinions.jsonl`, `personality.json`) — стримеру
  нужно «отношение к зрителю», ассистенту не нужно.
- **Сущности+junk-фильтр через эмбеддинг** (`add_entity_fact`): у него
  проверка на дубль делает N HTTP-запросов к Ollama на каждый факт. У нас
  и без этого 44% отказов `memory_add` (B8) — добавлять сетевые вызовы в путь
  записи нельзя.
- **Самоулучшение (`self_improve`)** — другая тема, не про память.
- **Эвикция старого шума** (`evict_stale_events`, раз в сутки): у него
  удаляет события старше 14-30 дней без чтений. Нам нельзя — правило «из базы
  ничего не удалять». Идею берём, реализацию — нет.

## Новые находки

### B14 — `add()` склеивает разные факты по пересечению слов

**Severity:** средняя. **Найдено:** при написании тестов B6/B12.

`MemoryService.add` без `supersedes_id` сливает запись с любой, у которой Jaccard
по словам ≥ 0.5. Два разных факта с общей формулировкой («Сервер X на Ubuntu»,
«Почта X на Fastmail») расходятся, но «Принтер стоит на кухне» и «Сканер стоит
на кухне» — уже нет: половина слов общая. Инструмент `memory_add` теперь
спрашивает (R33.2), а прямой `add()` — по-прежнему молча сливает.

**Проверка:** `sqlite3 harness.db "select id, content from memory where content like '%стоит%';"`

**Что делать:** порог поднять до 0.7 или требовать совпадения `area` и хотя бы
одного числа/пути. Не сделано: меняет поведение записи, нужен отдельный замер
на живой памяти.

### B15 — `memory_miss` почти перестал срабатывать

**Severity:** низкая. **Найдено:** после B12.

Fallback «свежее за 48 часов» заполняет пустой результат, поэтому строка
`memory_miss` теперь появляется только когда в окне нет вообще ничего. Это
следствие B12, а не поломка; если нужен счётчик промахов, его надо считать до
fallback.
