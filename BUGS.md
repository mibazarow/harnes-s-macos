## B24 — отказ БД оставляет перемещённый файл без записи корзины

**Severity:** высокая. `Services/FileSafetyService.swift`, `trash`.
Файл перемещался раньше INSERT в SQLite. При ошибке INSERT исходный путь
исчезал, а список корзины не содержал способа восстановления. Теперь ошибка
записи запускает обратное перемещение. Если и оно не удалось, ошибка содержит
путь к сохранённым данным; существующий файл по исходному пути не перезаписывается.

SQLite-триггер, запрещающий INSERT, воспроизвёл дефект. После исправления
оригинал остаётся на месте с прежним содержимым; AgentSafetyTests прошли.

**Проверка:** `xcodebuild -quiet -project Harness.xcodeproj -scheme Harness -configuration Debug -derivedDataPath .build -destination 'platform=macOS' -only-testing:HarnessTests/AgentSafetyTests test`

**Живым запуском не проверено.** Аварийное завершение процесса между файловой
операцией и записью SQLite по-прежнему требует отдельного восстановления.

## B23 — версия не восстанавливается после удаления оригинала

**Severity:** средняя. `Services/FileSafetyService.swift`, `restoreVersion`.
Безусловный removeItem прерывал восстановление отсутствующего файла. Теперь
удаление выполняется только для существующего пути. Новый регрессионный тест

**Проверка:** `xcodebuild -quiet -project Harness.xcodeproj -scheme Harness -configuration Debug -derivedDataPath .build -destination 'platform=macOS' -only-testing:HarnessTests/AgentSafetyTests test`

временный соседний файл и только затем вызывает replaceItemAt. Проверка с
нечитаемым снимком подтверждает сохранение текущего содержимого при ошибке
копирования. Обычная замена и восстановление отсутствующего файла также проходят.

# Правила для Kilo

Читать до первой строки кода. Здесь порядок работы, а не пожелания.

## С чего начинать

Открытых баг-пунктов по коду один: B17. Он меняет поведение записи при сжатии,
поэтому начинается с замера на живой памяти.

Дальше — только то, что найдёшь по факту из лога: сначала факт, потом правка.

## Чем заканчивать

Ничем «для галочки»: пустой пункт не открываем. Если по дороге нашёл дефект —
дописываешь сюда новым номером, с severity и командой проверки.

## Как считать пункт закрытым

- **Только живым запуском.** Тест зелёный — не доказательство. Пункт про логи
  закрыт, когда в `~/HARNES_S_DATA/logs/latency.log` появилась строка, которую
  там раньше не печатали, и Kilo её показал.
- **Пункт про базу** закрыт, когда приложена команда `sqlite3` и её вывод
  до/после. Не «поправил», а «было `10151`, стало `18568`».
- **Не выдавать сделанное за проверенное.** Если проверка требует твоего телефона,
  TCC-диалога или живой сессии — писать «живым запуском не проверено» жирным
  в отчёте, а не закрывать пункт.
- **Регрессия важнее фичи.** Если правка сломала сжатие на пустой истории —
  откат, а не «доделаю потом».
- **Закрытый пункт удаляется из файла** с короткой строкой в коммите: что
  сделано и каким коммитом закрыто. Файл не растёт могильником: сделанное,
  проверенное и забытое здесь не держим.

## Чего не делать

- **Миграции только добавляющие.** Новая колонка или новая таблица — да.
  Переименовать, поменять тип, удалить колонку — нет. Формат данных на диске
  не меняется (правило R30).
- **Из базы ничего не удалять.** Пустые assistant-записи чинятся фильтром на
  чтении, а не `DELETE`. Сжатие отвязывает историю от промпта — оно её не
  стирает. Это архитектурное свойство, а не случайность: на него завязано
  восстановление после провала.
- **Память удаляется только через `memory_forget`**, а не SQL-запросом.
- **Не трогать `bitrix/`** и не править вендорные зависимости.
- **Не переписывать `AGENTS.md`, `AGENT_PROCESS.md`** и не заводить S/M/L, часы
  и рубли в оценках.
- **Не править `project.yml` и `CODE_SIGN_IDENTITY`.** Release-сборка и
  нотаризация — отдельная процедура, не часть этих багов.
- **Не пушить.** Коммит по слову пользователя, push по слову пользователя.
- **Не писать новые файлы с задачами.** Всё новое, что нашёл по дороге,
  дописывается сюда, в `BUGS.md`, новым номером с severity и командой проверки.

## Правило трёх повторов

Если один и тот же подход провалился трижды — стоп. Записать в `BUGS.md`,
что именно пробовал и почему не вышло, и перейти к следующему пункту.
Долбить четвёртый раз запрещено: это трата времени и риск случайной порчи.

## B17 — сжатие помечает чужой факт как заменённый

**Severity:** средняя. **Найдено:** при закрытии B16 (19.11.2026).

`MemoryFactWriter` при сжатии ищет похожую запись через `similar(threshold: 0.5)`
и пишет новую строку с `supersedes_id`. Замена не удаляет старую строку, но
убирает её из поиска и промпта. Порог 0.5 ниже, чем был у `add()`, поэтому пара
вида

```
«Сервер альфа на Ubuntu 24.04» / «Сервер бета на Ubuntu 24.04»  → 0.714
```

помечает второй сервер как устаревшую версию первого: факт остаётся в базе, но
перестаёт находиться. B16 закрыл это для `add()`, здесь путь другой.

**Проверка:** дважды прогнать извлечение фактов на текстах выше и посмотреть
`select id, supersedes_id from memory order by id desc limit 4;` — вторая запись
не должна ссылаться на первую.

**Что делать:** перед заменой требовать совпадения субъекта, а не только
похожести: сравнивать content-токены, как в `add()` (`MemoryService.contentTokens`),
и заменять только когда различие — число, дата или версия при тех же остальных
словах. Иначе писать новую строку без `supersedes_id`.

**Почему не сделано сейчас:** меняет поведение сжатия, а замер требует прогона
извлечения на живой истории. Правило файла — сначала факт, потом правка.

## B18 — дедупликация меняет или скрывает самостоятельные факты

**Severity:** высокая. **Найдено:** 19.11.2026, изолированные регрессионные тесты.

В `MemoryService` токенизация отбрасывала односимвольные имена и числа:
`Server X runs Ubuntu` сливался с `Server Y runs Ubuntu`, а 2 процессора с 4.
Поиск по хешу не учитывал scope и supersedes: личный факт мог попасть в строку
workspace, а повтор старого факта возвращал скрытую из поиска историческую строку.

Четыре новых теста воспроизвели ошибки до исправления. Исправление сохраняет
односимвольные токены и ограничивает точную дедупликацию актуальными строками
нужного scope. Миграций и изменений живой базы нет.

**Проверка:** `xcodebuild -quiet -project Harness.xcodeproj -scheme Harness -configuration Debug -derivedDataPath .build -destination 'platform=macOS' -only-testing:HarnessTests/MemoryMergeRuleTests test`

**Живым запуском не проверено.** Пункт не закрыт.

## B19 — сжатие сдвигает историю после ошибки записи

**Severity:** высокая. **Найдено:** 19.11.2026, `ChatStore+Compaction.swift`, путь `compact`.

Сохранение checkpoint, границы и счётчика выполнялось тремя отдельными записями
с подавлением ошибок (`try?`). Даже после ошибки БД состояние в памяти обновлялось
и сжатие возвращало успех. После перезапуска документ и граница могли расходиться.

Теперь `saveCheckpoint` сохраняет все три значения одной транзакцией; ошибка
доходит до обработчика сжатия до изменения состояния в памяти. Перед записью
проверяется отмена задачи. Формат данных не менялся.

Два новых теста сначала упали, затем прошли: согласованность границы со счётчиком
и откат checkpoint при принудительной ошибке SQLite-триггера. Смежные тесты
границ и политики сжатия также прошли.

**Проверка:** `xcodebuild -quiet -project Harness.xcodeproj -scheme Harness -configuration Debug -derivedDataPath .build -destination 'platform=macOS' -only-testing:HarnessTests/SummaryBoundaryTests -only-testing:HarnessTests/SummaryBoundaryIDTests -only-testing:HarnessTests/CompactionPolicyTests test`

**Живым запуском не проверено.** Пункт не закрыт.
