# WINDOWS_PORT — HARNES-S для Windows

Документ для того, кто будет делать Windows-версию: что переносим, на чём, в каком порядке и где
будут грабли. Написан по факту существующего кода macOS-версии, а не по общим представлениям о том,
«как бывает».

- Исходник: `macOS_AGENT_HARNESS` (Swift 6, SwiftUI, GRDB/SQLite, `15 651` строка Swift).
- Цель: отдельное нативное приложение для Windows 11 с тем же поведением, той же папкой данных и
  тем же списком инструментов.
- Сборка идёт на Windows-машине. Разработка Windows-версии не должна ломать macOS-версию.

---

## 0. Короткий ответ на главный вопрос

**Стек: C# 14 / .NET 10 + WinUI 3 (Windows App SDK).**

Почему именно он:

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **C# + WinUI 3** | Нативно, без браузера; ONNX Runtime, SQLite с FTS5, WinRT OCR и захват экрана — из коробки; нормальный XAML для виртуализированного чата | XAML-верстка многословна, часть API WinRT требует interop | **Выбран** |
| C# + Avalonia | Тот же C#, одна кодовая база на Windows/Linux/macOS | Не нативный контроль, свои контролы, хуже интеграция с системой | Запасной, если захочется Linux |
| Rust + Tauri | Маленький бинарник, быстрый | UI — WebView2, то есть ровно тот «браузер в окне», против которого написано всё приложение | Отклонён |
| Rust + egui / Slint | Нативно и быстро | Богатый текст, выделение, IME, доступность — всё руками; markdown-транскрипт будет хуже | Отклонён |
| Swift for Windows | «Тот же язык» | SwiftUI на Windows нет; остаётся голый WinRT-интероп, то есть худшее из двух миров | Отклонён |
| Electron / Flutter | Быстрый старт | 150+ МБ рантайма, вторая копия текста в JS, перерисовка по токену — прямая противоположность заявленной боли проекта | Отклонён |

**Ключевое решение по архитектуре: два нативных приложения, один контракт.** Ядро на Swift не
переписываем на общий язык и не тащим через FFI. Вместо этого фиксируем общий контракт (схема БД,
раскладка папки данных, текст системного промпта, имена и схемы инструментов, формат скиллов,
формат `mcp.json`) и реализуем его дважды — идиоматично на каждой платформе.

Причина простая: ядро — это ~10 тысяч строк логики, из которых половина — работа с файлами,
процессами и SQLite. FFI-слой между Swift и C# стоит дороже, чем второй аккуратный порт, и
превращает любой баг в «а чей это слой?». А текстовые контракты (промпт, инструменты, скиллы)
дешёво расшарить файлами.

## 2. Отдельный репозиторий

Windows-версия — **отдельный репозиторий**, а не папка внутри этого. Общего дерева исходников,
общего `git` и общих коммитов нет: две независимые кодовые базы, каждая со своими remote.

Это осознанно: macOS-версия рабочая и не должна получать риск от порта, а Windows-версия не должна
тащить `.xcodeproj`, Swift-модули и macOS-специфику, которую никто не будет поддерживать.

### 2.1 Имена и remote

| | macOS | Windows |
|---|---|---|
| репозиторий | `harnes-s-macos` | `harnes-s-windows` |
| Gitverse | `git@gitverse.ru:mibazarow/harnes-s-macos.git` | `git@gitverse.ru:mibazarow/harnes-s-windows.git` |
| GitHub | `https://github.com/mibazarow/harnes-s-macos.git` | `https://github.com/mibazarow/harnes-s-windows.git` |

Правило двух зеркал сохраняется: любой пуш идёт в оба remote параллельно (`git pushall`).
Оба Windows-репозитория создаются пустыми в момент первого пуша.

### 2.2 Раскладка Windows-репозитория

```
harnes-s-windows/
├── Harness.sln
├── src/
│   ├── Harness.App/            # WinUI 3, только UI
│   ├── Harness.Core/           # всё остальное, без зависимости от WinUI
│   └── Harness.Core.Tests/     # xUnit
├── packaging/
│   ├── Harness.Package/        # MSIX
│   └── assets/                 # иконки, шрифт Nordwand Mono
├── docs/
│   ├── WINDOWS_PORT.md         # этот файл (копия)
│   ├── CONTRACT.md             # §3–§6: схема БД, папка данных, инструменты
│   └── screenshots/            # снимки macOS-версии как эталон вида
├── contract.json               # машинный контракт: инструменты, схемы, версия БД
├── AGENTS.md
└── README.md
```

Правило: `Harness.Core` не ссылается на `Microsoft.UI.Xaml`. Всё, что нужно UI, приходит через
модели и события. Это то, что делает ядро тестируемым без окна — и это же главный урок
существующей кодовой базы.

### 2.3 Как завести репозиторий

Папка этого проекта копируется на Windows-машину целиком, после чего из неё вычищается всё
macOS-специфичное. На macOS для этого есть скрипт:

```bash
Scripts/seed_windows_repo.sh ~/harnes-s-windows
```

Он собирает чистую папку без Swift-исходников, `Harness.xcodeproj`, `project.yml`, `.build`,
`DOCS/github-token.md` и без `.git` — то есть готовую к `git init` и первому коммиту.

Внутри неё остаётся:

- `WINDOWS_PORT.md` — инструкция для того, кто будет делать порт;
- `ВОСПРОИЗВОДИМОЕ_ТЕХНИЧЕСКОЕ_ЗАДАНИЕ.md` — полная спецификация поведения macOS-версии;
- `DOCS/screenshots/*.png` — эталон внешнего вида;
- `Resources/Fonts/` — Nordwand Mono;
- `shared-seed/skills/` — те же `SKILL.md`, что установлены в приложении;
- `contract.json` — имена, схемы инструментов, версия схемы БД и хеш базового промпта.

Чего в ней нет и почему: Swift-кода (переписывается), `.git` (история другой ветки разработки),
токенов (у каждой машины свой), `Scripts/` для macOS-сборки.

### 2.4 Как две версии не разъедутся

Общего кода нет, но контракт должен совпадать. Механика — файл `contract.json`:

1. В macOS-приложении есть Debug-команда `--export-contracts`, которая пишет `contract.json`:
   версия схемы БД, список таблиц и колонок, имена и JSON-схемы 46 инструментов, хеш текста
   базового промпта, версия формата `mcp.json`.
2. Файл копируется в Windows-репозиторий и лежит в корне.
3. В Windows-репозитории тест `ContractParityTests` читает `contract.json` и сверяет с тем, что
   реально зарегистрировано в `Harness.Core`: набор имён, схемы параметров, версию БД.
4. При любом изменении контракта на Mac файл перегенерируется и коммитится в Windows-репозиторий
   отдельным коммитом «sync contract».

Это дешевле общей папки и не связывает две сборки. Расхождение видно на тестах, а не в проде.

## 3. Контракт данных

### 3.1 Папка данных

Windows: `%USERPROFILE%\HARNES_S_DATA\` — та же структура и те же имена, что на macOS.

```
HARNES_S_DATA/
├── database/harness.db
├── config/mcp.json
├── config/skills/**
├── config/gsd/            (опционально, если ставим GSD)
├── workspace/
├── models/embeddinggemma-2/
├── tools/                 (Playwright, node_modules)
├── artifacts/
├── versions/
├── trash/
├── logs/
└── backups/
```

Смысл: папку можно скопировать с Mac на Windows и обратно. Для этого:

- пути внутри БД хранить абсолютными, но **не полагаться** на них при старте: индекс и версии
  пересобираются, если путь не найден;
- переводы строк в текстах нормализовать при чтении и записи (`\r\n` → `\n`), иначе диффы и
  подсветка поедут;
- кодировка — UTF-8 без BOM на запись, BOM допускается на чтение;
- разделители пути принимать оба (`/` и `\`) во всех аргументах инструментов и нормализовать
  через `Path.GetFullPath`.

### 3.2 Схема БД

Схема переносится один в один, миграции v1–v8 включительно. Таблицы: `providers`, `secrets`,
`memory`, `memory_fts` (FTS5), `embeddings`, `messages`, `indexed_files`, `file_versions`,
`trash`, `app_state`, плюс лениво создаваемые `schedules` и `todos`.

Критичные детали, которые легко потерять:

```sql
CREATE VIRTUAL TABLE memory_fts USING fts5(
    content,
    content='memory',
    content_rowid='id',
    tokenize='unicode61 remove_diacritics 2'
);
```

- Нужен **FTS5**. В C# берём `Microsoft.Data.Sqlite` + `SQLitePCLRaw.bundle_e_sqlite3`: этот
  бандл собирает SQLite с FTS5, в отличие от системного `winsqlite3.dll` из Windows.
- Триггеры `memory_ai` / `memory_ad` / `memory_au` обязательны, иначе FTS разъедется с таблицей.
- `PRAGMA journal_mode=WAL`, `PRAGMA busy_timeout=5000`, `PRAGMA foreign_keys=ON`.
- Индекс `idx_providers_default` — частичный (`WHERE is_default = 1`), ровно как на Mac.
- Колонка `temperature REAL NOT NULL DEFAULT 0.2` у провайдера (v8).
- `secrets.value` — обычный TEXT. Осознанное решение: на Mac секреты лежат в открытом виде, чтобы
  папка данных оставалась переносимой. На Windows **не переходим** на DPAPI, иначе папка перестанет
  открываться на другой машине. Вместо шифрования — ACL: папка доступна только текущему
  пользователю (см. §9.3). Это надо явно написать в README Windows-версии, чтобы не было
  иллюзий.

## 4. Ядро: что и как переносить

### 4.1 Провайдер (Core/LLM)

`HttpClient` + `HttpCompletionOption.ResponseHeadersRead`. Разбор SSE:

- .NET 9+ содержит `System.Net.ServerSentEvents.SseParser` — начинать с него;
- если упрёмся в особенности провайдеров (комментарии-пинги, `data:` без пробела, чанки,
  разрезанные между пакетами) — писать свой построчный парсер, как в Swift: он умеет собирать
  событие из нескольких `data:` строк, отбрасывать `:`-пинги и держать буфер между чтениями.

Тело запроса — те же поля и в том же порядке, что в Swift:

```json
{
  "model": "…",
  "stream": true,
  "temperature": 0.2,
  "reasoning_effort": "medium",
  "messages": [],
  "tools": [],
  "stream_options": { "include_usage": true }
}
```

- `temperature` — из карточки провайдера (по умолчанию `0.2`, диапазон `0…2`);
- `reasoning_effort` не передаётся при `off`;
- `tools` не передаётся, если пусто;
- `usage` приходит последним чанком — из него берутся `prompt_tokens`, `prompt_cache_hit_tokens`,
  `prompt_cache_miss_tokens` для лога латентности.

Стрим разбирается в события: `delta(text)`, `delta(reasoning)`, `toolCall(index, id, name, argsFragment)`,
`usage`, `done`, `error`. Дальше это то же, что на Mac: UI обновляет текущее сообщение, ядро
копит `tool_calls` по индексу.

Ошибки классифицировать так же: `isContextOverflow` по коду 400/413/422 **и** тексту
(`context length`, `too long`, `maximum context`, `tokens >`). От этого зависит один агрессивный
ретрай компакции.

### 4.2 Агентский цикл

Один в один по `Core/Agent/AgentLoop.swift`:

1. Собрать системный промпт в порядке «стабильное → изменчивое»: база → скиллы → память →
   чекпоинт → автопилот → стиль (последним).
2. Спланировать окно (`ContextComposer`): бюджет = окно модели − системный промпт − схемы
   инструментов − запас на ответ.
3. Отправить, стримить, собрать `tool_calls`.
4. Выполнить инструменты, каждый — отдельным сообщением-трассой; результат обрезать по лимитам.
5. Повторить, максимум 100 шагов, с мягким сообщением о продолжении.
6. Защиты: отказ без попытки, «готово» без вызова инструмента, заявления о невозможном,
   зацикливание по паре «вызов + результат».

Формулы, которые нельзя «улучшить» по дороге:

- хвост истории: `max(2000, 12% бюджета)` токенов, граница — по сообщению пользователя, чтобы не
  разрезать пару «вопрос — ответ»;
- порог компакции по умолчанию 80% окна, диапазон настройки 50–95%;
- при переполнении: одна попытка с хвостом вдвое короче, после трёх неудач — пауза 10 минут;
- саммари — по семи разделам (цель, требования, решения, состояние работы, следующий шаг, важные
  файлы, важный контекст), лимит 16 000 символов, по 2 000 символов с сообщения;
- пачки для саммари: `окно/4`, зажатые в 8 000–60 000 токенов;
- из БД при компакции **ничего не удаляется**.

### 4.3 Память и поиск

- Запись: консолидация по Jaccard ≥ 0.5 обновляет существующую запись, а не плодит дубль.
- Пины (`pinned`) идут первыми и не вытесняются; затухание по времени для неиспользуемых.
- Поиск: FTS5 `bm25` + косинус по эмбеддингам, слияние через RRF (k = 60).
- Эмбеддинги: EmbeddingGemma 2, 768 измерений, L2-норма, локально.
- Пока модель не скачана — честная деградация до FTS, без блокировки инструментов и без ошибки
  на весь ход.

### 4.4 Эмбеддинги и ONNX

`Microsoft.ML.OnnxRuntime` (CPU). Файлы те же, из `onnx-community/embeddinggemma-300m-ONNX`,
ревизия закреплена хешем — как в `EmbeddingModelInstaller.swift`:

| Файл | Куда | Размер |
|---|---|---|
| `tokenizer_config.json` | `models/embeddinggemma-2/` | ~1,1 МБ |
| `tokenizer.json` | `models/embeddinggemma-2/` | ~20 МБ |
| `onnx/model_quantized.onnx` | `models/embeddinggemma-2/model_quantized.onnx` | ~0,6 МБ |
| `onnx/model_quantized.onnx_data` | `models/embeddinggemma-2/model_quantized.onnx_data` | ~309 МБ |

Важно: **кормить только те входы, которые объявлены в графе**. Экспорт бывает двух видов —
мультимодальный (хочет `image_features`, `video_features`, `audio_features`) и текстовый (их не
принимает). На Mac это уже исправлено чтением `session.inputNames`; на C# делать так же:
`session.InputMetadata.Keys`.

### 4.5 ⚠️ Токенизатор — главный технический риск

`tokenizer.json` — SentencePiece-BPE с byte fallback (Gemma). Варианты, по порядку проверки:

1. **`Microsoft.ML.Tokenizers`** — `BpeTokenizer.Create(path)`. Проверить, что кириллица
   кодируется корректно и что byte fallback работает.
2. **HuggingFace `tokenizers`** через P/Invoke к `tokenizers.dll` (сборка под win-x64 есть).
3. **`onnxruntime-extensions`** — в нём есть токенизатор, но привязка к Python-миру, для C# неудобно.
4. Портировать пре-токенизатор руками (последний вариант, ~300 строк).

**Критерий приёмки спайка:** прогнать 100 строк (русский, английский, код, эмодзи, хвостовые
пробелы) через Mac-версию и через Windows-версию и сравнить **последовательности token id**.
Совпадение побайтово. Если не совпало — качество эмбеддингов поедет незаметно, и это будет
худший вид бага: всё работает, только ищет плохо.

Не начинать остальную работу, пока этот тест не зелёный.

### 4.6 Компакция и стиль

Компакция — это обычный запрос к той же модели с отдельным промптом, без инструментов. Ничего
платформенного, переносится текстом.

Стиль (`Core/Style`):

- EMA с прогревом `1/n` на первых 10 наблюдениях, затем α = 0.15;
- недельное затухание, чтобы человек, переставший материться, перестал отражаться;
- признак попадает в промпт только при достаточном числе наблюдений **и** повторяемости по
  разным дням;
- блок ≤ 360 символов, строки безопасности резервируются первыми;
- «краткость» детектируется, но **не** рендерится в промпт: длину задаёт температура;
- карточка тона — не раньше 20 сообщений и не чаще раза в 6 часов.

## 5. Инструменты: 46 штук

Имена и JSON-схемы копируются из `Core/Agent/ToolDefinitions.swift` **дословно** — это то, что
видит модель. Меняется только реализация.

### 5.1 Общие правила

- Лимиты вывода: команда — 30 000 символов, чтение файла — 20 000, листинг — 400 записей,
  описание MCP-инструмента — 600 символов. Обрезка помечается, чтобы модель знала.
- Все тексты инструментов и ошибок — на русском, как на Mac.
- Каждый мутирующий инструмент делает снапшот в `versions/` и умеет откат.
- Удаление — в собственную `trash/`, а не в корзину Windows: так поведение одинаково на обеих
  платформах и откат предсказуем.
- `writeGuard`: запрет записи в `C:\`, `C:\Windows`, `C:\Program Files`, `C:\Program Files (x86)`,
  `C:\ProgramData`, `%LOCALAPPDATA%`, `%APPDATA%`, `%USERPROFILE%\AppData`, а также в корни любых
  других дисков (`D:\` и т.п.). Разрешены обычные пользовательские пути и рабочая папка.

### 5.2 Таблица соответствий

| Инструмент | Windows-реализация | Замечания |

### 5.3 Чего на Windows нет и что вместо

- **iMessage, AppleScript, `open -a`, `pbcopy`** — соответствующих инструментов в списке и нет,
  но проверить, что нигде не осталось вызовов `osascript`.
- **`.app`-бандлы** — нет; пути к ресурсам через `AppContext.BaseDirectory`.
- **Keychain** — не используем (см. §3.2).
- **`/bin/bash`** — заменяется PowerShell; все примеры в промпте для `bash` проверить на
  PowerShell-синтаксис. Это точка, где модель будет спотыкаться чаще всего.

## 6. MCP на Windows

stdout/stdin-транспорт, как на Mac, но с двумя системными особенностями:

1. **`.cmd` и `.bat` нельзя запустить напрямую** через `Process.Start` с `UseShellExecute=false`.
   Если сервер объявлен как `npx`, реально это `npx.cmd` → запускать через
   `cmd.exe /c npx …` либо резолвить полный путь к `.cmd` и запускать `cmd.exe /c "<path>" …`.
2. **Кодировка.** Явно `StandardOutputEncoding = UTF8`, `StandardInputEncoding = UTF8`,
   `StandardErrorEncoding = UTF8`. Иначе кириллица в аргументах и ответах превратится в мусор.

Остальное — один в один: `initialize` → `notifications/initialized` → `tools/list` → `tools/call`,
таймаут 60 с, логи в `logs/mcp-<name>.log`, гашение всех процессов при выходе из приложения.

## 7. Windows-специфика, которая съест время

### 7.1 Процессы

- `CreateNoWindow = true`, `UseShellExecute = false`, перенаправление всех трёх потоков.
- `StandardOutputEncoding = UTF8`; для `pwsh` дополнительно `-NoLogo -NoProfile -NonInteractive`
  и `[Console]::OutputEncoding=[Text.Encoding]::UTF8` в начале команды.
- Дерево процессов: при отмене убивать всё дерево (`Process.Kill(entireProcessTree: true)`),
  иначе `pwsh` оставит висеть дочерние.
- Таймауты: 120 с по умолчанию, kill всего дерева.

### 7.2 PowerShell вместо bash

Модель привыкла к bash и будет писать `ls`, `grep`, `rm -rf`, `&&`, `$VAR`. В PowerShell:

- `&&` работает в PowerShell 7, но не в 5.1 — требуем **PowerShell 7**;
- `ls`/`rm`/`cp` — алиасы, работают; `grep` — нет (`Select-String`);
- `$VAR` — своя семантика, `$env:VAR` — переменные среды;
- пайпы другие.

Решение: оставляем имя инструмента `bash` (иначе модель растеряет привычки и начнёт путаться),
но в описании первым предложением пишем: «On Windows this runs PowerShell 7». Плюс в системный
промпт Windows-версии добавляем короткий блок с отличиями. Это единственное место, где промпт
платформенно-зависим.

### 7.3 Пути и файлы

- Разделители: принимать оба, отдавать `\` в UI и `Path.Combine` внутри.
- Длинные пути (> 260): манифест `longPathAware=true`, и всё равно проверять.
- Блокировки: антивирус может держать файл — писать через временный файл и `File.Move(overwrite)`,
  повторять 3 раза с паузой.
- Регистр: файловая система нечувствительна к регистру, а Unix-код на это опирается. Все сравнения
  имён — `OrdinalIgnoreCase`, но **ключи в БД и имена скиллов** хранить как есть.

### 7.4 DPI и окно

- Per-monitor v2 DPI awareness в манифесте.
- Заголовок: `ExtendsContentIntoTitleBar = true` + `SetTitleBar`, кнопки окна рисует система.
- Фон — сплошной `#0D0D10`, без Mica/Acrylic: тема Copper рассчитана на ровный тёмный фон.
- Минимальный размер окна — 900×600; стартовый — 1260×900 (как на скриншотах README).

## 8. UI: как повторить Copper

Токены переносятся из `Core/Theme/Theme.swift` в `ResourceDictionary`:

| Токен | Значение | Где |
|---|---|---|
| `bg` | `#0D0D10` | фон окна |
| `panel` | `#16161A` | панели, композер |
| `accent` | `#B87333` | акцент, встроенный код, полоса сообщения пользователя |
| `userText` | `#E2D8CD` | текст пользователя |
| `assistantText` | `#CFC4B8` | текст ответа |
| `dim` | приглушённый | служебное |
| `border` | тонкая рамка | разделители |
| `codeBackground` | фон блока кода | — |

Обязательные детали паритета:

- **Встроенный код** — цветом `accent`, без фона. Это отдельно просили и отдельно чинили.
- **Диффы** — построчно: `+` акцентом, `-` приглушённым, `@@` и заголовки файлов отдельным цветом.
- **Размышления** — свёрнутая строка `> размышления · N симв.`, раскрывается по клику, по
  умолчанию закрыта.
- **Блок кода** — кнопка копирования при наведении.
- **Сообщение пользователя** — слева, с медной полосой; ответ — с тонкой серой.
- **Порядок**: шапка (папка, модель) → транскрипт → композер → футер (провайдер, заполнение окна).

### 8.1 Транскрипт

- `ItemsRepeater` (или `ListView` с рециклингом) внутри `ScrollView`; в памяти 200 сообщений,
  старше — страницами по 200 из SQLite при прокрутке вверх.
- Каждое сообщение — свой `RichTextBlock` (даёт выделение текста) внутри `Border` с фоном.
- Стриминг: не пересобирать markdown на каждый токен. Накапливать в `StringBuilder`, обновлять
  визуал по таймеру 30–50 мс, финальный парсинг — по завершении абзаца/ответа.
- Автоскролл «прилипает» к низу, если пользователь у низа; если он ушёл вверх — не дёргать.

### 8.2 Markdown

`Markdig` для разбора → собственный слой блоков (параграф, заголовок, список, таблица, цитата,
код, картинка) → рендер в WinUI. Не рендерить markdown в HTML в `WebView`: это лишний движок и
потеря нативного выделения.

Подсветку кода проще **портировать имеющуюся** (`Core/Highlight/SyntaxHighlighter.swift`, 243
строки, regex-движок: Swift, JS/TS, Python, JSON, shell, SQL, HTML/CSS, YAML, diff), чем
подключать TextMateSharp с грамматиками VS Code: меньше зависимостей, тот же вид, тот же набор
языков.

### 8.3 Композер

`TextBox` с `AcceptsReturn`, `Enter` — отправить, `Shift+Enter` — перенос, `Esc` — остановить
поток. Drag-and-drop файлов с превью-чипами. `/` в пустом поле открывает палитру команд —
`AutoSuggestBox` + `Popup`, источник команд — тот же `CommandCatalog`.

## 9. Сборка, установка, обновление

### 9.1 Что нужно на Windows-машине

- Windows 11 22H2+ (на 10 тоже пойдёт, но не проверяем).
- Visual Studio 2022/2026 с workload **WinUI application development** (Windows App SDK).
- .NET 10 SDK.
- Git for Windows (и `git.exe` в PATH).
- PowerShell 7 (`pwsh`).
- Node.js LTS — для MCP-серверов и Playwright.
- Python 3.12+ — только если понадобятся скрипты скиллов.

### 9.2 Сборка

```powershell
dotnet restore Harness.sln
dotnet build Harness.sln -c Debug
dotnet test  src/Harness.Core.Tests
dotnet run   --project src/Harness.App
```

Релиз:

```powershell
dotnet publish src/Harness.App -c Release -r win-x64 --self-contained `
  -p:PublishSingleFile=false -p:WindowsPackageType=MSIX
```

### 9.3 Установщик

- **MSIX** предпочтителен: чистое удаление, обновления, ярлык, ассоциации.
- Подпись: самоподписанный сертификат для личного использования. Для распространения — обычный
  code-signing сертификат (деньги).
- При первом запуске: создать `%USERPROFILE%\HARNES_S_DATA\`, выставить ACL «только текущий
  пользователь», начать фоновую докачку EmbeddingGemma 2 (~330 МБ) с прогрессом в футере.
- Портативный режим: `HARNESS_DATA_DIR` как override (в Release — нет, только в Debug, как на Mac).

## 13. С чего начать в первый день

1. Поставить VS с WinUI workload, .NET 10, Git, PowerShell 7, Node.
2. Взять папку, подготовленную `Scripts/seed_windows_repo.sh`, переименовать в `harnes-s-windows`,
   выполнить `git init`, создать два пустых remote и запушить.
3. `dotnet new winui3` → пустое окно с заголовком «HARNES-S» и фоном `#0D0D10`.
4. `Microsoft.Data.Sqlite` + `bundle_e_sqlite3` → создать схему v8 по `docs/CONTRACT.md`,
   прогнать `SELECT` по `memory_fts` (убедиться, что FTS5 есть).
5. `HttpClient` + `SseParser` → отправить один запрос к своему провайдеру и вывести дельты в
   `TextBlock`.
6. **Токенизатор**: загрузить `tokenizer.json`, закодировать 100 строк, сравнить с Mac.
7. Если 6 зелёный — импортировать `contract.json` в тесты и идти в M1.

## 14. Что считать успехом

Windows-версия считается портированной, когда на чистой машине можно:

1. Установить приложение из MSIX и запустить без консоли.
2. Настроить провайдера и получить ответ с рассуждениями и вызовом инструмента.
3. Открыть реальный проект, найти в нём код, поправить файл, прогнать тесты, закоммитить и
   запушить в два remote.
4. Спросить «что мы решали в прошлый раз» — и получить ответ из памяти, а не из истории чата.
5. Провести разговор на 300 сообщений и не увидеть «контекст переполнен».
6. Подключить MCP-сервер и вызвать его инструмент.
7. Скопировать папку `HARNES_S_DATA` с Mac на Windows (и обратно) и продолжить работу с той же
   памятью, скиллами и настройками.
8. Прогнать `dotnet test` — 100+ тестов, 0 падений.
