# HARNES-S — ВОСПРОИЗВОДИМОЕ ТЕХНИЧЕСКОЕ ЗАДАНИЕ

Файл: `ВОСПРОИЗВОДИМОЕ_ТЕХНИЧЕСКОЕ_ЗАДАНИЕ.md`. Этого документа достаточно, чтобы воспроизвести приложение с нуля на другой машине.

**Версия:** 3.4 (описывает реализованное состояние)
**Назначение:** по этому документу приложение воспроизводится с нуля другой командой или моделью.
**Статус:** всё, что описано ниже без пометки «план», реализовано и покрыто тестами. Планы на будущее вынесены в отдельные документы: `COMPUTER_USE_TZ.md` (управление компьютером).

---

## 0. Что это

Нативное приложение для macOS: один чат с постоянной памятью, работой с кодом, браузером, зрением и терминальным интерфейсом. Без списка сессий, без боковых панелей, без привязки к конкретному облаку.

Один пользователь, одна машина, один диалог. Всё управление — через чат и настройки.

### 0.1 Границы

Входит:

- стриминг ответов и размышлений любой [OI]-совместимой модели;
- агентский цикл с инструментами;
- постоянная память с полнотекстовым и семантическим поиском;
- работа с файлами, git, сборкой и тестами;
- доступ в интернет и управление браузером;
- распознавание изображений и текста;
- секреты в локальной базе;
- адаптация к манере речи пользователя;
- MCP-серверы;
- скиллы;
- расписания.

Не входит (сознательно):

- несколько чатов и их синхронизация;
- мобильные и веб-клиенты;
- многопользовательский режим и роли;
- облачные песочницы и удалённые машины;
- LSP-диагностика;
- плагинный рантайм;
- голосовой ввод.

## 1. Требования и сборка

- macOS 27+, Apple Silicon.
- Xcode 27+.
- XcodeGen (`brew install xcodegen`).
- Опционально: Node.js — для Playwright и GSD; `php` — для линта PHP; ImageMagick (`brew install imagemagick`) — только если пересобираешь иконку.

```bash
xcodegen generate
xcodebuild -project Harness.xcodeproj -scheme Harness -configuration Debug -derivedDataPath .build build
open .build/Build/Products/Debug/Harness.app
```

Тесты:

```bash
xcodebuild -project Harness.xcodeproj -scheme Harness -derivedDataPath .build -destination 'platform=macOS' test
```

Релиз:

```bash
xcodebuild -project Harness.xcodeproj -scheme Harness -configuration Release -derivedDataPath .build build
codesign --verify --deep --strict .build/Build/Products/Release/Harness.app
rm -rf /Applications/Harness.app
cp -R .build/Build/Products/Release/Harness.app /Applications/
xattr -dr com.apple.quarantine /Applications/Harness.app
```

Проект генерируется из `project.yml`. Пакеты: GRDB (SQLite), swift-markdown, swift-transformers (токенизатор), onnxruntime-swift-package-manager, шрифт Nordwand Mono (MIT) в бандле.

Иконка: исходник `Resources/AppIconSource.png` (1024×1024), `Scripts/make_icons.sh` генерирует все 10 размеров в `Resources/Assets.xcassets/AppIcon.appiconset`. Артворк вписывается в сетку Apple: 824 px контента на канвасе 1024, отступ 100, радиус 185, маска по альфе. Скрипт нужен только при замене иконки; в сборке участвует уже готовый `Assets.xcassets`.

Bundle ID: `app.project-s.swift`. Display name: `HARNES-S`.

```
  Theme/      палитра, шрифты, настройки

  App/        пути, ошибки конфигурации

              безопасность файлов, история, MCP-конфиг, каталог провайдеров
Storage/      схема SQLite и миграции
Models/       доменные модели, ChatStore
```

Правила слоёв:

- UI не знает про SQL и сеть, только про `ChatStore` и сервисы.
- Сервисы — `actor` или `Sendable` структуры; UI вызывает их через `await`.
- `ChatStore` — `@MainActor @Observable`, единственный владелец состояния чата.
- Чистые алгоритмы (контекст, патчи, стиль, защиты) не зависят от AppKit и базы, поэтому тестируются без запуска приложения.

## 3. Данные

Корень: `~/HARNES_S_DATA/`, создаётся при первом запуске.

```
HARNES_S_DATA/
├── database/harness.db
├── config/
│   ├── mcp.json
│   ├── gsd/                 # gsd-core/ и scripts/ — рантайм GSD
│   └── skills/              # SKILL.md в подпапках; .disabled выключает скилл
├── workspace/
├── models/embeddinggemma-2/
├── tools/                   # Playwright и его node_modules
├── artifacts/
├── versions/
├── trash/
├── logs/
└── backups/
```

Правила:

- Перенос на другую машину = копирование папки.
- Эмбеддинги — всегда EmbeddingGemma 2: `models/embeddinggemma-2/` (`model_quantized.onnx`, `model_quantized.onnx_data`, `tokenizer.json`, `tokenizer_config.json`), 768 измерений, локально, без сети и оплаты. Выбора бэкенда нет: провайдерского `/embeddings` в коде не осталось.
- Внутри `.app` весов нет. После установки приложение само скачивает их с Hugging Face в `models/embeddinggemma-2/` — см. §3.4. Так бандл остаётся маленьким, а папка данных остаётся единственным переносимым артефактом.
- Playwright ставится в `tools/` при необходимости: `cd ~/HARNES_S_DATA/tools && npm i playwright@1.63.0 && npx playwright install chromium`. Без него инструмент `browser` честно сообщает, чего не хватает.

| `is_default` | INTEGER | один основной, гарантируется уникальным индексом |
| `kind` | TEXT | `openai_compatible` по умолчанию |
| `auth_kind`, `auth_header` | TEXT | способ авторизации, `bearer` по умолчанию |
| `cheap_model` | TEXT | дешёвая модель для служебных проходов, может быть пустой |
| `headers_json` | TEXT | дополнительные заголовки |
| `input_price`, `output_price` | REAL | цены, для отображения |
| `enabled` | INTEGER | включён ли провайдер |
| `health`, `last_check_at` | | результат проверки |
| `created_at`, `updated_at` | TEXT | ISO8601 |

`secrets`:

| Поле | Смысл |
|---|---|
| `alias` | уникальный, без учёта регистра |
| `value` | сам секрет |
| `note` | чем является |
| `created_at`, `updated_at` | |

`memory`:

| Поле | Смысл |
|---|---|
| `scope` | `user` / `workspace` |
| `content` | текст |
| `kind` | `fact` / `decision` / `preference` / `pattern` / `code` |
| `tags` | JSON-массив |
| `source` | откуда пришло |
| `workspace_root` | для `scope=workspace` |
| `pinned` | 1 — пользователь сказал запомнить, запись неприкосновенна |
| `hits` | сколько раз запись попадала в промпт |
| `last_used_at` | последнее обращение; по нему идёт вытеснение |
| `content_hash` | SHA-256 текста, для точной дедупликации и переиспользования вектора |

`memory_fts` — FTS5 по `content`, `tokenize='unicode61 remove_diacritics 2'`, синхронизируется триггерами на INSERT/UPDATE/DELETE.

`embeddings` — `(ref_kind, ref_id, model)` PK, `dim`, `vector` BLOB (float32), `text_hash`, `updated_at`. `text_hash` позволяет взять готовый вектор для того же текста, не вызывая модель.

`indexed_files` — `path` PK, `hash` (SHA-256 содержимого), `updated_at`. По ней индексатор пропускает неизменившиеся файлы.

`messages` — `role`, `text`, `reasoning`, `created_at`.

`app_state` — key/value: чекпоинт компакции, профиль стиля, прочие настройки рантайма.

`file_versions` и `trash` создаются миграцией `v7`; `schedules` и `todos` — миграцией `v9`.

### 3.2 Миграции

`DatabaseMigrator` с версиями: `v1` (базовая схема), `v2_reasoning_level`, `v3_embed_model`, `v4_messages`, `v5_memory_lifecycle` (`pinned`, `hits`, `last_used_at`), `v6_index_reuse` (`content_hash`, `indexed_files`), `v7_recovery_tables` (`file_versions`, `trash`), `v8_provider_temperature` (`temperature` у провайдера), `v9_indexes_and_lazy_tables` (индексы запросов, `schedules` и `todos` переехали из ленивого DDL), `v10_message_exchanges` (`messages.exchanges` — вызовы инструментов и результаты, чтобы они переживали перезапуск). Каждая проверяет наличие колонки перед `ALTER`, поэтому применяется к любой существующей базе без ошибок.

### 3.3 Скриншоты и демо-режим

README показывает шесть сценариев работы. Чтобы они были воспроизводимы, а не нарисованы руками, в Debug-сборке есть демо-диалоги:

### 3.4 Загрузка модели эмбеддингов

Источник — репозиторий `onnx-community/embeddinggemma-300m-ONNX`, ревизия закреплена хешем в `EmbeddingModelDownload.revision`, поэтому смена содержимого ветки `main` не может подменить веса незаметно.

| Файл в репозитории | Куда кладётся | Размер |
|---|---|---|
| `tokenizer_config.json` | `tokenizer_config.json` | ~1,1 МБ |
| `tokenizer.json` | `tokenizer.json` | ~20 МБ |
| `onnx/model_quantized.onnx` | `model_quantized.onnx` | ~0,6 МБ |
| `onnx/model_quantized.onnx_data` | `model_quantized.onnx_data` | ~309 МБ |

- Старт — при запуске приложения, в фоне (`EmbeddingModelInstaller.startIfNeeded`), параллельно с открытием чата.
- Порядок файлов: сначала мелкие, веса последними. Признак «установлено» — наличие всех четырёх, поэтому недокачанная модель никогда не выглядит готовой.
- Наличие проверяется по минимальному размеру, а не по точному: уже установленный экспорт другой ревизии не перекачивается на 309 МБ ради совпадения байт. Точный размер проверяется только у свежескачанного файла.
- Прогресс виден в футере композера: `эмбеддинги 42%`; по завершении в чат приходит строка о включении семантики, при ошибке — строка с причиной.
- Пока модель не готова, поиск не блокируется: `memory_search` работает по FTS, индексатор пишет «эмбеддинги недоступны — индексирую только текст». Следующий вызов после загрузки уже использует векторы.
- Обрыв загрузки не ломает установку: следующий запуск видит, каких файлов не хватает, и докачивает только их.
- Сеть нужна один раз. Дальше модель работает локально; для машин без интернета папку `models/embeddinggemma-2/` можно скопировать вручную.

## 5. Чат

### 5.1 Поведение

- Один диалог. История хранится в `messages` и восстанавливается при запуске: последние 100 реплик, остальные подгружаются при прокрутке вверх.
- `Return` — отправить, `Shift+Return` — перенос строки.
- Пока идёт ответ, новые сообщения встают в очередь и обрабатываются по одному; в футере видно «в очереди: N».
- Очередь живёт внизу транскрипта отдельным блоком, а не в общей ленте: иначе каждый новый шаг работающего ответа выталкивал бы твоё сообщение вверх. Пока сообщение в очереди, оно полупрозрачное и помечено плашкой «в очереди» с часами; в запрос к модели не попадает. Когда наступает черёд — уходит в ленту как обычное и начинает обрабатываться.
- `Esc` — остановить ответ и очистить очередь. Снятые сообщения переносятся в ленту с плашкой «не отправлено», чтобы текст не потерялся, и в чат приходит уведомление, сколько их было.
- Кнопка остановки одновременно служит индикатором работы: вокруг квадрата вращается дуга акцентом. Наведение подсвечивает квадрат, подсказка гласит «Идёт работа · нажми, чтобы остановить (Esc)».
- `⌘⇧K` — очистить вид (база не трогается).
- `⌘⇧P` — режим плана: все мутирующие инструменты отключены на уровне исполнения.
- План (`todos`) принадлежит ходу, который его создал: он очищается при отправке нового сообщения и вручную — кнопкой × в полосе плана или пунктом меню «Очистить план». Раньше он сохранялся в базе и висел под транскриптом бесконечно.
- `⌘↓` — прыжок в конец чата; кнопка появляется только когда прокрутка не внизу и пользователь сам отлистал.
- Во время ответа транскрипт сам держится за низ: рост текста, размышлений и трейсов не отключает автопрокрутку. Отключает её только ручной скролл вверх; возврат к низу или новая отправка включают снова. Автоскролл ограничен ~25 раз в секунду, чтобы не дёргался.
- Пока не пришло ни одного токена, в пузыре стоит «думает…». Как только пошли размышления или вызовы инструментов, надпись исчезает: индикатор нужен только чтобы не было пустоты, а не как счётчик.
- `⌘,` — настройки.

### 5.2 Вложения

- Drag&drop в поле ввода и кнопка-скрепка.
- Изображения показываются превью, уходят в модель как `image_url` base64.
- Текст читается и подставляется в контекст как `<file name="..." path="...">…</file>`.
- Прочие файлы передаются путём.
- Вложить можно и целую папку: диалог выбора папки кладёт в контекст путь и дерево, а не содержимое.
- Лимит на файл — 64 МБ.

### 5.3 Размышления

Если провайдер отдаёт `reasoning_content` или `reasoning`, текст идёт в отдельный блок: свёрнут по умолчанию, жёлтый, по клику раскрывается. Содержимое не смешивается с ответом.

### 5.4 Трейс инструментов

Каждый вызов показывается строкой в сообщении: иконка по типу, имя, короткий аргумент, состояние. Ошибки помечаются. Скриншоты и снимки страниц показываются превью прямо в трейсе.

### 5.5 Оформление markdown

Метрики: межстрочный интервал ≈152% от кегля (0.20 em дополнительного leading сверх естественной высоты шрифта), абзац 20 pt снизу, код 12 сверху и 24 снизу, цитата и таблица по 16, горизонтальная черта — 32 pt воздуха без линии. Абзацный отступ увеличен с 12 до 20 pt после того, как leading стал плотнее: без этого соседние абзацы сливались в одну портянку. Соседние вертикальные отступы схлопываются: берётся больший, а не сумма.

Заголовки — плоская лестница:

| Уровень | Размер | Вес | Сверху / снизу |
|---|---|---|---|
| `#` | тело + 3 | semibold | 28 / 12 |
| `##` | тело + 1 | semibold | 24 / 10 |
| `###` | тело | semibold | 20 / 8 |
| `####` и ниже | тело | regular, приглушённый | 20 / 8 |

Шаг фиксированный в пунктах, а не множитель: при теле 14 это 17/15/14 — как у них. Множитель 1.45 при шрифте 20 давал 29, и ответ выглядел раздутым.

Остальное:

- Списки: отступ маркера 32 pt, между пунктами 8, вложенный список — 16 pt. Маркер приглушён.
- Блок кода: без шапки с языком. Плашка `#1B1A1E`, рамка, скругление 6, внутренние отступы 14/12. Кнопка копирования проявляется при наведении в правом верхнем углу и исчезает через 1,2 с после нажатия.
- Инлайн-код: цвет основного текста на подложке 8% от него же, без отдельного акцентного цвета — строка с несколькими вставками читается как одна фраза.
- Таблица: заголовок приглушённый, 13 pt, строки через одну с лёгкой подложкой, разделители 1 px.
- Цитата: вертикальная линия 1 px цветом рамки, отступ 8, текст приглушён.
- Горизонтальная черта не рисуется — только отступ.
- Картинки: локальные из файла, удалённые через `AsyncImage`, ширина по контейнеру, скругление 4.

В промпте отдельно запрещены заголовки в обычном ответе: структуру дают нумерованные шаги, списки и жирные лид-ины. Заголовки остаются для длинных документов.

## 6. Агентский цикл

`AgentLoop` — асинхронный поток событий:

| Событие | Что значит |
|---|---|
| `stepStarted` | начался новый запрос к модели; граница сообщения в транскрипте |
| `delta` | кусок текста ответа |
| `reasoning` | кусок размышлений |
| `toolStarted` | вызов начат |
| `toolFinished` | вызов завершён, есть результат и ошибка |
| `usage` | расход токенов из финального чанка: `prompt`, `cacheHit`, `cacheMiss` |
| `completed` | цикл закончен |

Правила:

- Цикл идёт до отсутствия вызовов инструментов или до отмены пользователем. Есть мягкий потолок в 100 шагов: `LoopGuard` ловит только идентичный повтор, а модель, которая каждый раз зовёт инструмент чуть иначе, прошла бы мимо. При достижении лимита агент останавливается с понятным сообщением, и разговор можно продолжить. Потолок снимается передачей `maxSteps: nil`.
- История накапливает assistant-сообщения с `tool_calls` и tool-сообщения с результатами. Внутри одного хода они живут в памяти цикла, а между ходами — в поле `exchanges` сообщения: на следующем ходу вызовы и результаты проигрываются обратно провайдеру, иначе модель не видит, что уже сделала, и начинает задачу заново. Обмены хранятся в базе (миграция v10, колонка `messages.exchanges`) и переживают перезапуск; вывод инструмента при сохранении обрезается до 4000 символов.
- Каждый запрос к модели — отдельный шаг и отдельное сообщение в транскрипте. `AgentLoop` шлёт событие `stepStarted`, по нему UI закрывает предыдущий пузырь и открывает новый. Поэтому размышление, вызовы инструментов и текст каждого шага не смешиваются: получилось «размышление → ответ → инструменты → размышление → ответ», а не растущая простыня, где новое рассуждение копится над уже прочитанным ответом.
- Пустой шаг (без текста, размышлений и вызовов) в транскрипт не попадает: пузырь удаляется.
- Разделитель между шагами не нужен: границей служит сам пузырь.
- Отмена — через `Task.cancel()`, доводится до конца каждого шага.

### 6.1 Защита от зацикливания

`LoopGuard` сравнивает пару: сигнатура вызовов (имя + аргументы) и сигнатура прогресса (имя + успех/ошибка + первые 160 символов результата). Ловятся две формы: одинаковый шаг три раза подряд (`A A A`) и короткий цикл без прогресса (`A B A B`, `A B C A B C`) — вторая встречается чаще, это классическое «прочитал → поправил → прогнал тест → прочитал». Цикл ищется в окне из 12 шагов, период до 3. Легитимные повторы с меняющимся результатом (счётчик, мигание, ожидание условия) не прерываются: прогресс обязан совпадать.

### 6.2 Защиты честности

- `NoAttemptGuard` — если модель отказалась, не сделав ни одного вызова, ей передаётся одно корректирующее сообщение и запускается ровно один дополнительный ход.
- Сэмплинг: кроме `temperature` в запрос уходят `presence_penalty` 0.2 и `frequency_penalty` 0.15. Одна температура 0.2 — это почти жадное декодирование, а жадное декодирование на длинном ответе уходит в дегенеративный повтор. Штрафы намеренно мягкие: код легитимно повторяет отступы, `self.`, скобки и идентификаторы. Если провайдер отвергает эти поля (400 с упоминанием параметра), запрос повторяется один раз без них, с той же температурой.
- `max_tokens` как потолок вывода: 8192 без размышлений, 16384 с ними.
- `finish_reason` разбирается. `length`, `max_tokens` и `content_filter` означают «ответ обрезан»: шаг останавливается, под сообщением появляется предупреждение. Продолжать цикл в этом случае нельзя — модель не видела конца собственного текста и начнёт с начала, что и выглядело как зацикливание.
- Потолок вывода инструментов внутри одного хода: 160 000 символов (~40k токенов). При превышении самые старые результаты заменяются заглушкой, свежие остаются. Без этого ход на сотню шагов сам себя переполнял окно.
- `RepetitionGuard` — ловит вырождение генерации: модель начинает повторять слово, фразу или целую строку и не останавливается. Проверяется и текст ответа, и размышления: reasoning-цикл сжигает токены до первого видимого символа. Это известный сбой низкотемпературного сэмплинга на длинных ответах, и `LoopGuard` его не видит, потому что инструменты не вызываются. Проверка идёт по хвосту потокового текста (окно 1200 байт, с шагом 250 байт) и распознаёт три формы: блок длиной до 300 байт, повторённый ≥4 раз; ≥6 одинаковых строк подряд длиной от 20 символов; ≥14 одинаковых слов подряд. Повтор вырезается целиком с начала серии, под ответом появляется предупреждение. Работа идёт по UTF-8 байтам, а не по графемам: повтор — свойство байтов, и сравнение байтов на порядок дешевле.
- `FalseSuccessGuard` — если модель заявила об успехе при нуле вызовов (а просьба была на действие) или при последней ошибке инструмента, под ответом показывается предупреждение. Обе стороны якорятся: просьба — императив в начале предложения или инфинитив после «можешь/нужно/надо/давай», заявление — «Готово/Сделано/Выполнено», первое лицо прошедшего времени или пассив с конкретным объектом («файл создан»), и только в первых 400 символах ответа. Без якорей подстрочный поиск срабатывал на обычных объяснениях («файл создаётся», «готово к записи») и приучал игнорировать предупреждение. Предупреждение хранится в отдельном поле сообщения и не уходит обратно в модель как часть её же ответа.
- `CapabilityClaimGuard` — заявления о недоступных действиях (отправка письма, звонок, перезагрузка) сопровождаются припиской с реальным положением дел.
- `AssistantTextSanitizer` — удаляет из готового ответа утёкшие `<thinking>…</thinking>`, строки-маркеры («Размышляю:», «План:») и навигационный мусор вроде «Мне нужно вызвать инструмент…». Незакрытый тег удаляется сразу, чтобы рассуждение не мигало на экране.

## 7. Контекст и компакция

`ContextComposer` — чистая функция, строит план окна:

- бюджет = `contextWindow × threshold / 100 − reserve`, где `reserve` = 4000 токенов под ответ, минимум 512;
- в план входят системный промпт (вместе с памятью, стилем, индексом скиллов и чекпоинтом), чекпоинт-саммари и хвост истории (не меньше 6 сообщений);
- всё, что не влезло, помечается как компактируемое.

Оценка токенов — `TokenEstimator`: около 3 символов на токен для смеси русского, английского и кода.

Отправка в модель строится по этому же плану, а не по фиксированному числу сообщений: в запрос попадает столько последних сообщений, сколько влезает в бюджет. Размышления и трейсы инструментов в запрос не уходят — только текст реплик. Вложения учитываются в текущей реплике: текст до 20 000 символов, картинки — как изображения.

Память приложения:

- в базе хранятся все сообщения; при запуске восстанавливаются последние 100, вложения не сохраняются;
- при прокрутке вверх подгружается страница по 200 более старых сообщений (`ChatHistoryService.older(than:limit:)`), пока история не кончится; позиция чтения сохраняется, загрузка показывается индикатором;
- база работает в режиме WAL (`synchronous = NORMAL`), поэтому чтения не ждут запись, а мелкие транзакции индексатора не создают журнал на диск;
- в оперативной памяти держится не больше 200 реплик, старые вытесняются из вида, но остаются в базе;
- после завершения хода полезная нагрузка вложений (`data`) освобождается, остаются имя, путь и превью.

Компакция:

1. Сжимаемый фрагмент режется на пачки по бюджету `окно/4`, но не меньше 8 и не больше 60 тыс. токенов, и уходит в модель последовательно, с накоплением: каждая следующая пачка получает предыдущее саммари. Один общий запрос не влез бы в модель, к которой он же и адресован.
2. Транскрипт для сжатия обрезается: сообщение длиннее 4000 символов сохраняет края, середина заменяется пометкой «обрезано N символов». Оригинал остаётся в базе.
3. Модель возвращает **структурное** саммари по шаблону: Цель, Требования, Решения, Состояние работы (Готово / В работе / Блокеры), Следующий шаг, Важные файлы, Важный контекст. Свободный пересказ теряет именно то, что нужно для продолжения: что сделано, что мешает и где лежат файлы. Правила: короткие однострочные пункты, точные пути, символы, команды и тексты ошибок, без упоминания самого сжатия, не больше 600 слов.
4. Саммари ограничено 16 тыс. символов: с каждым слиянием оно иначе растёт и в итоге стоит дороже, чем экономит.
5. Саммари сохраняется в `app_state` вместе с числом покрытых сообщений.
6. В чат добавляется системное уведомление с числами.
7. Из базы не удаляется ничего.

Граница компакции. `ChatStore` помнит последнее сообщение, вошедшее в саммари (`compactedThroughID`), и в запрос его уже не отправляет — иначе саммари и исходный текст дублировались бы. При перезапуске граница восстанавливается из счётчика покрытых сообщений и общего числа строк в `messages` (`ChatStore.coveredInView(total:covered:inView:)`).

Предполётная компакция. Перед отправкой строится план по тому же набору сообщений, что уйдёт в модель. Если план что-то отрезает, это сначала сжимается, затем план пересчитывается, и только потом уходит запрос. Это то, что делает безопасным переключение с модели на 800k на модель на 250k: без предполётной компакции первый же запрос молча потерял бы половину истории, и модель никогда не узнала бы, что в ней было. Если сжать не удалось, в чат приходит предупреждение с числом сообщений, которые не попадут в запрос, — без тихой потери.

Автоматическая компакция после ответа остаётся: она убирает второй запрос к модели до первого токена в обычном режиме. Предполётная срабатывает только когда история реально перестала влезать — после большого вложения или смены модели.

Ручная компакция: `/compact` сжимает всё, кроме хвоста, и хвост считается **в токенах**, а не в сообщениях: 12% бюджета, но не меньше 2000 токенов, с выравниванием границы по сообщению пользователя. Шесть коротких реплик и шесть длинных — очень разные объёмы живого контекста.

Хвост в автоматическом плане тоже выравнивается по сообщению пользователя: ответ, с которого начинается окно без своего вопроса, читается как висящая реплика.

Обработка отказа провайдера. Если провайдер вернул ошибку «слишком длинный контекст» (400/413/422 с упоминанием context length, too long, maximum context и подобным), приложение не показывает её сразу: оно сжимает историю жёстче — порог 50% вместо обычного — и повторяет запрос один раз. Если сжимать нечего (единственное сообщение само больше окна), в чат приходит честное объяснение. Определение — `ProviderError.isContextOverflow`.

Защита от трэшинга. Неудачное сжатие ставит кулдаун: 2 минуты, после трёх подряд — 10 минут. Пока кулдаун активен, предполётная компакция пропускается и пишет в `logs/latency.log` строку `preflight compaction skipped: cooldown`; повторять сломанное сжатие на каждом ходу — значит удваивать стоимость разговора, который и так в беде. Ручной `/compact` кулдаун игнорирует: это явная просьба пользователя.

Смена окна между ходами пишется в `logs/latency.log` строкой `window A -> B: preflight compaction`.

Порог берётся из настроек (`compactionThresholdPercent`, по умолчанию 80). В футере постоянно виден счётчик `использовано / окно`, при превышении порога он подсвечивается.

### 7.1 Задержка до первого токена

Приложение не должно задерживать ответ своей работой. Локальная подготовка запроса — сборка системного промпта, чтение памяти, индекс скиллов, схемы инструментов — укладывается в единицы миллисекунд благодаря кешам. Остальное время до первого токена — префилл и размышления на стороне провайдера.

Каждый запрос пишет две строки в `logs/latency.log`:

```
2026-11-06T19:20:11Z prep=12ms prompt=42133ch messages=13 model=…
2026-11-06T19:20:17Z first_token=5940ms
```

`prep` — время локальной подготовки, `prompt` — размер отправленного текста, `first_token` — сколько ждал первый байт от провайдера. По этим числам видно, где именно теряется время.

### 7.2 Кэш промпта

Большой системный промпт и схемы инструментов отправляются каждый раз, и это нормально: платят не за размер, а за то, попал ли префикс в кэш провайдера. У OpenAI-совместимых endpoint'ов (включая DeepSeek) кэш префикса включён автоматически: если начало запроса совпадает с предыдущим байт в байт, провайдер не считает его заново и отвечает заметно быстрее. Отдельного флага для этого нет — задача приложения в том, чтобы префикс не менялся.

Правила, которые соблюдаются:

- Порядок частей системного промпта: базовый промпт → индекс скиллов → память → чекпоинт → автопилот → стиль. Всё, что меняется редко, стоит выше; блок стиля, который сдвигается почти на каждом сообщении, стоит последним.
- Память в промпте упорядочена стабильно: сначала закреплённые, затем по `id`. Обращение к записи обновляет `last_used_at`, но не меняет порядок — иначе префикс ехал бы каждый ход.
- Список инструментов не меняется в течение сессии: MCP-дескрипторы загружаются один раз (прогрев при старте) и дальше берутся из кеша. Инструмент, появившийся на втором ходу, обнулил бы кэш целиком.
- Индекс скиллов кешируется и пересобирается только при изменении набора скиллов.
- История в запросе — растущий хвост: старые сообщения не переписываются, поэтому общий префикс остаётся валидным.
- Блок стиля заморожен: он пересчитывается раз в 20 ходов, а не после каждого сообщения. Иначе он сдвигал бы весь хвост истории и обнулял кэш на каждом ходе.
- Компакция выполняется после ответа и меняет только блок чекпоинта — то есть влияет на префикс один раз, а не каждый ход. Предполётная компакция при смене модели меняет префикс ещё один раз, и это неизбежно: старый префикс всё равно не помещается в новое окно.

Диагностика в `logs/latency.log`:

```
prep=12ms prompt=42133ch messages=13 model=…
first_token=5940ms
cache hit=38000 miss=4133 prompt=42133 (90%)
```

`cache hit` — сколько токенов провайдер взял из кэша, `miss` — сколько посчитал заново. Если hit близок к нулю от хода к ходу, префикс нестабилен: ищи, что изменилось выше по списку.

## 8. Провайдеры

- Любой endpoint с `POST /chat/completions` и SSE.
- Поля: имя, Base URL, токен, модель, окно контекста, уровень размышлений, температура, признак «основной». Модель эмбеддингов не настраивается: она одна и встроена.
- Кнопка «Проверить и загрузить модели» вызывает `GET /models` с `Authorization: Bearer`, показывает список; при ошибке — текст ошибки.
- Размышления передаются как `reasoning_effort`: `off` не передаётся, дальше `low` / `medium` / `high`.
- Температура задаётся отдельно у каждого провайдера, по умолчанию `0.2`, диапазон `0…2` с шагом `0.05`. Краткость и собранность достигаются сэмплингом, а не инструкциями «отвечай коротко» в промпте: такие инструкции тратят токены и портят стиль. Значение хранится в колонке `temperature` таблицы `providers` (миграция v8).
- Ошибки провайдера выводятся в чат как есть, а не подменяются заглушкой.
- Удаление основного провайдера передаёт роль следующему по времени создания.
- Имя активного провайдера и модели показывается в футере композера.

Формат запроса:

```json
{
  "model": "…",
  "stream": true,
  "temperature": 0.2,
  "reasoning_effort": "medium",
  "messages": [{"role": "user", "content": "…"}],
  "tools": [{"type": "function", "function": {"name": "…", "description": "…", "parameters": {}}}],
  "tool_choice": "auto"
}
```

Изображения передаются частями `{"type": "image_url", "image_url": {"url": "data:image/png;base64,…"}}`.

Разбор потока: строки `data:`, `[DONE]`, дельты `choices[0].delta.content`, `reasoning_content`, `tool_calls` (аргументы склеиваются по `index`), `finish_reason`.

`apply_patch` принимает только `@@`-хунки; при несовпадении контекста возвращает номер строки, ожидаемое и фактическое содержимое. Вместо текста патча можно передать `patch_file` — путь к готовому диффу.

### 9.4 Знания и агент

`memory_add`, `memory_search`, `memory_forget`, `memory_list`, `secret_save`, `secret_get`, `secret_search`, `skill_list`, `skill_read`, `skill_install`, `mcp_list`, `mcp_tools`, `todowrite`, `todo_read`, `schedule_add`, `schedule_list`, `schedule_remove`, `task` (изолированный подагент), плюс все инструменты MCP как `mcp__<server>__<tool>`.

Всего встроенных инструментов 46; MCP-инструменты подмешиваются к ним динамически под именами `mcp__<server>__<tool>`. Схема отправляется каждый запрос, поэтому описания короткие, а подробности (`mcp_tools`, `skill_read`) загружаются вызовом.

`memory_add` принимает `text`, `kind` и `pinned`; `pinned: true` ставится, когда пользователь сказал «запомни», и делает запись неприкосновенной. `memory_forget` удаляет по id или по формулировке. `memory_list` даёт id для точечных операций.

`task` запускает отдельный цикл со своим контекстом, без доступа к секретам и планировщику, и возвращает только итог.

### 9.5 Режим плана

Белый список наоборот: при включённом режиме из схемы удаляются и блокируются `fs_write`, `edit_file`, `apply_patch`, `trash_paths`, `restore_trashed`, `restore_version`, `git_commit`, `git_stash`, `bash`, `schedule_add`, `schedule_remove`, `memory_add`, `memory_forget`, `secret_save`, `skill_install`, `index_workspace`, `todowrite` и все MCP-инструменты. Проверка выполняется в момент вызова, а не только при формировании списка.

Запись защищена отдельно от режима плана: `writeGuard` отказывает в записи в `/`, `/System`, `/usr`, `/bin`, `/sbin`, `/etc`, `/Library`, `/Applications` и в служебные каталоги приложения (`database`, `config`, `logs`, `models`, `versions`, `trash`, `backups`). Обычные пользовательские пути — Documents, Desktop, любая папка проекта — разрешены: блокировать их было бы вреднее, чем полезно.

Некорректный JSON аргументов возвращается как ошибка с текстом «невалидный JSON» и фрагментом входа, а не как «не хватает параметра»: иначе модель чинит несуществующую проблему.

Код инструментов разложен по файлам: `ToolRegistry.swift` — состояние, схемы, роутер, `ToolRegistry+Files/Shell/Web/Code/Recovery/Agent/Knowledge/Skills.swift` — реализации. Файл роутера — около 200 строк вместо 1037.

## 10. Память

### 10.1 Запись

- Дедупликация в два шага: сначала точное совпадение по `content_hash` (SHA-256 текста), затем Jaccard по множествам слов (длиной от 2 символов). При совпадении ≥ 0.5 запись обновляется, а не дублируется; хеш обновляется вместе с текстом.
- После записи считается эмбеддинг и кладётся в `embeddings` вместе с `text_hash`. Если вектор для такого же текста уже есть, он переиспользуется без прогона модели.
- `/remember` и `memory_add` индексируют запись одинаково: без вектора запись находилась бы только по полному тексту.
- Решение «запоминать или нет» принимает модель по правилам из системного промпта: сохраняются устойчивые предпочтения, соглашения проекта, резкие поправки пользователя и принятые решения; не сохраняются разовое состояние задачи, догадки, содержимое файлов и секреты. Явное «запомни» ставит `pinned = 1` и не может быть вытеснено.
- `memory_forget` удаляет запись по id или по текстовому запросу; закреплённые записи удаляются только при явном указании на них. `memory_list` показывает id для точечных операций.
- `/memory forget`, `/memory pin`, `/memory unpin` делают то же из чата.

### 10.2 Чтение

- В системный промпт попадают 40 записей в стабильном порядке: сначала закреплённые, затем по `id`. Обращение помечает записи использованными (`hits + 1`, `last_used_at`), но порядок не меняет — иначе префикс промпта ехал бы каждый ход и обнулял кэш провайдера.
- Саморефлексия: при запуске удаляются незакреплённые записи без единого обращения старше 90 дней, а вместе с ними — осиротевшие векторы. Явно закреплённое не трогается никогда.
- `memory_search` — гибридный поиск: FTS5-ранжирование и косинус по эмбеддингам, слияние через взаимное ранжированное объединение (RRF, k = 60).
- Вектор запроса кешируется (8 последних), поэтому повторный поиск не вызывает модель.
- Сравнение — `vDSP_dotpr`, строки читаются курсором без материализации всех векторов в словарь; недостающие записи подтягиваются одним `IN`-запросом, а не по одной.
- Удаление записи удаляет её вектор.
- Если эмбеддингов нет, поиск работает только по FTS и не падает.

### 10.3 Эмбеддинги

- По умолчанию локальная модель EmbeddingGemma 2 через ONNX Runtime: 768 измерений, L2-нормализация, вход до 512 токенов, пулинг по `sentence_embedding`.
- Токенизатор — swift-transformers.
- Батч до 8 текстов за один прогон модели: паддинг до максимальной длины, маска внимания отсекает паддинг. Если модель отказывается от батча, автоматический откат на поштучный режим.
- Если локальной модели нет, используется `/embeddings` провайдера.
- Векторы хранятся как float32 BLOB вместе с `text_hash`; одинаковый текст не считается повторно.

### 10.4 Индексация рабочей папки

- Обход с пропуском `.git`, `node_modules`, `.build`, `build`, `dist`, `vendor`, `.venv`, `Pods`, `DerivedData`, `.next`, `target`, `__pycache__`.
- Текстовые расширения: код, разметка, конфиги, документация.
- Инкрементальная индексация: SHA-256 содержимого файла хранится в `indexed_files`; неизменившийся файл пропускается целиком.
- Файл режется на чанки по 1200 символов с перекрытием 200. Граница выбирается по переводу строки, затем по пробелу, в последней пятой части окна, поэтому чанк редко рвёт слово или оператор.
- Каждый чанк — запись `memory` с `kind=code` и `scope=workspace`, дедуплицированная по `content_hash`, плюс эмбеддинг.
- Векторы одинаковых чанков переиспользуются: модель вызывается только для нового текста, и все новые чанки файла уходят одним батчем.
- Если эмбеддинги недоступны, индексация всё равно выполняется текстом, с той же дедупликацией и тем же пропуском неизменившихся файлов.

## 12. Адаптация к манере речи

### 12.1 Что измеряется

`StyleAnalyzer` на каждом сообщении пользователя:

| Сигнал | Как определяется |
|---|---|
| обращение | местоимения «ты» или «вы» |
| краткость | длина ≤ 60 символов |
| сленг | словарь разговорных слов |
| мат | по лексикону |
| эмодзи | диапазоны Unicode |
| пунктуация | «!!», многоточие, строчная первая буква, отсутствие точки в длинном тексте |
| директивность | глаголы-приказы в первых словах |

### 12.2 Профиль

- Хранится в `app_state` как JSON: счётчики, признаки, карточка, ручная карточка, режим.
- Обновление — экспоненциальное сглаживание: первые 10 наблюдений вес `1/n`, дальше 0.15.
- Хранятся до 14 различных дней на признак.
- Затухание: 5% в неделю от последнего срабатывания; ниже 0.2 спустя 2 недели признак удаляется.

### 12.3 Активация

Признак попадает в промпт только при одновременном выполнении:

- минимум 8 наблюдений и минимум 2 разных дня (для сленга 3 дня, для мата 5 срабатываний и 4 дня);
- доля срабатываний выше порога (краткость 0.6, сленг 0.15, эмодзи 0.25, пунктуация 0.3, директивность 0.4, обращение 0.65).

Один вечер не меняет персону — это обязательное требование, покрытое тестом.

### 12.4 Рендер

`StyleBlockBuilder` вставляет в конец системного промпта блок:

```
СТИЛЬ (только форма; факты и безопасность выше):
- Обращайся на «ты», по-дружески, без официоза.
- Другим людям пиши нейтрально; стиль не переноси в письма, коммиты и документы.
```

Признак краткости детектируется в профиле, но в промпт не рендерится: длину ответа задаёт температура провайдера (§8), а не инструкция «отвечай коротко».

- Жёсткий лимит 360 символов.
- Обязательные строки (про третьих лиц и ограничения мата) резервируются первыми, их нельзя вытеснить длинной карточкой.
- Режимы: `auto` — профиль; `neutral` — блок не рендерится; `manual` — только карточка пользователя.
- Карточка пользователя проверяется лексиконом: оскорбления и слэры не попадают в промпт.

### 12.5 Карточка тона

Отдельный проход модели по последним 20 сообщениям пользователя (до 300 символов каждое, не более 4000 всего):

- запускается не раньше 20 сообщений всего;
- не чаще раза в 6 часов;
- не в режиме `neutral`;
- возвращает одну строку: 1–3 черты через запятую;
- нормализуется (кавычки, маркеры списка, длина до 160) и отбрасывается при жёсткой лексике.

### 12.6 Лексикон

Три класса: мягкий мат, оскорбления, слэры. Оскорбления и слэры никогда не переносятся и подавляют счётчик мягкого мата в том же сообщении. Есть нормализация похожих латинских букв и цифр и список ложных срабатываний.

## 13. Скиллы

- Каталог: `config/skills/<name>/SKILL.md`.
- Встроенные: `Resources/skills/builtin/` — только чтение.
- Формат: frontmatter (`name`, `description`, `version`, `triggers`, `allowed-tools`) и тело.
- Установка: локальная папка, файл `SKILL.md`, прямой URL на `.md`. Архивы и репозитории без файла не поддерживаются.
- Замена существующего — только с `--force`.
- Включение и выключение — маркер `.disabled`, файлы не удаляются.
- Пользовательский скилл с тем же именем перекрывает встроенный.

Встроенные скиллы (`self-config`, `passwords`, `memory`, `coding`, `web-browser`) лежат в бандле и доступны только для чтения. Все остальные скиллы живут в `config/skills` и не вшиваются в приложение: их можно ставить по одному или залить набором. Утилита `Scripts/install_skills.py` раскладывает внешние папки в `~/HARNES_S_DATA/config/skills`, нормализует frontmatter (в том числе свёрнутые `description: >`), убирает `@`-префиксы include-строк, вычищает личные пути и заменяет их плейсхолдерами.

GSD-скиллы устанавливаются той же утилитой с флагом `--include-gsd`; рантайм копируется рядом с каталогом скиллов:

```bash
python3 Scripts/install_skills.py --include-gsd --gsd-runtime ~/.config/kilo ~/.config/kilo/skills/gsd-*
```

Раскладка: `config/gsd/gsd-core/` и `config/gsd/scripts/` (второй нужен, потому что `gsd-tools.cjs` требует `../../../scripts/fix-slash-commands.cjs`). В тексте GSD-скиллов пути переписаны на `~/HARNES_S_DATA/config/gsd/gsd-core`, а `@`-include-строки превращены в обычные пути: агент читает их через `fs_read` перед стартом. Каждый GSD-скилл получает блок адаптации к HARNES-S: `<arguments>` — текст после имени скилла, именованных подагентов нет (роль передаётся в `task` вместе с `agents/<role>.md`), инструмента `question` нет (вопросы задаются в чате), имена инструментов маппятся на `fs_read`/`fs_write`/`edit_file`/`bash`/`fs_glob`/`fs_grep`/`todowrite`/`task`. Рантайм запускается как `node ~/HARNES_S_DATA/config/gsd/gsd-core/bin/gsd-tools.cjs <command>`; состояние — в `.planning/` проекта. Если рантайма нет, скилл честно сообщает, что GSD Core не установлен.

Индекс скиллов кешируется в памяти и пересобирается только при установке, удалении и переключении скилла: сканирование ~120 манифестов на каждый запрос давало задержку до первого токена. Описание в индексе обрезается до 60 символов — этого хватает, чтобы выбрать скилл по имени, а полный текст отдаёт `skill_read`. На 118 скиллах индекс занимает около 4,1 тыс. символов и больше не упирается в лимит, скрывая часть записей.

В системный промпт попадает только индекс включённых скиллов — имя и сокращённое описание, не более 8000 символов. Скиллы, у которых общий префикс до первого дефиса и их пять и больше (например `gsd-*`), схлопываются в одну строку вида `- gsd-* (72): add-tests, ai-integration-phase, …`, чтобы индекс не разрастался. Тело загружается по требованию инструментом `skill_read`, который возвращает инструкции, абсолютный путь каталога и список вложенных файлов (тело — до 60 000 символов). Плейсхолдер `<skill-dir>` в тексте скилла означает этот путь. Выключенные скиллы в индекс не попадают; всё, что не влезло в лимит, сворачивается в строку «… and N more; call `skill_list`».

## 14. MCP

- Конфиг: `config/mcp.json`, список `servers`.
- Поля сервера: `name`, `transport` (`stdio` / `http` / `sse`), `command`, `args`, `url`, `env`, `enabled`, `exposure`, `scope`. Работает только stdio; http и sse объявлены в модели, но клиент их не поднимает.
- Порядок: `initialize` → `notifications/initialized` → `tools/list` → `tools/call`.
- Таймаут запроса 60 с, логи в `logs/mcp-<name>.log`.
- Инструменты подмешиваются как `mcp__<server>__<tool>`.
- `exposure: "deferred"` (по умолчанию) отдаёт в схему только имя, короткое описание (≤ 600 символов) и список аргументов с пометкой обязательных, а сама схема — `{"type":"object","additionalProperties":true}`. Полную JSON-схему агент получает инструментом `mcp_tools`. `exposure: "full"` отправляет исходную схему целиком.
- Сессии поднимаются лениво. `RootView` вызывает `warmUpMCP()` при старте, поэтому к первому сообщению дескрипторы обычно уже готовы. Если прогрев ещё не закончился, первый запрос ждёт его: список инструментов не должен меняться между ходами, иначе кэш префикса обнуляется.
- Версии пакетов фиксируются явно, чтобы поведение не менялось между запусками.

Команды: `/mcp`, `/mcp add <имя> <команда…>`, `/mcp add <имя> --url <адрес>`, `/mcp remove|enable|disable`.

Пример `mcp.json`:

```json
{"servers": [{"name": "scrapling", "transport": "stdio", "command": "/path/to/scrapling-mcp",
  "args": [], "env": {}, "enabled": true, "exposure": "deferred", "scope": "global"}]}
```

## 16. Безопасность и обратимость

- Рабочая папка — основное место работы. Запись за её пределами разрешена в обычные пользовательские каталоги (Documents, Desktop, папки проектов), но запрещена в системные и служебные: `/`, `/System`, `/usr`, `/bin`, `/sbin`, `/etc`, `/Library`, `/Applications` и каталоги данных приложения. Проверка — `writeGuard` в `ToolRegistry`.
- Каждая правка файла предваряется снапшотом в `versions/`; имя содержит метку времени и короткий уникальный суффикс.
- Удаление — перемещение в `trash/` с записью в базе, восстановление по id.
- Секреты не попадают в логи и промпт.
- Креды проекта (например, `dbconn.php` в Битриксе) не выводятся.
- Автопилот отключает подтверждения, но не отключает перечисленные запреты.

### 17.2 Шрифт

- По умолчанию Nordwand Mono, встроен в бандл, регистрируется при старте.
- В настройках можно выбрать любую установленную гарнитуру и размер 11–20. Межстрочный интервал фиксирован (`AppFont.lineSpacing` = 0.20 em): настраивать его отдельно нельзя, чтобы шрифт и интервал не влияли друг на друга непредсказуемо.
- При отсутствии выбранного шрифта используется системный моноширинный.

### 17.3 Раскладка

- Шапка 38 pt: имя приложения, рабочая папка, кнопка режима плана, настройки.
- Транскрипт: сообщения на всю ширину с отступом 15 pt по краям, зазор между сообщениями 10 pt.
- И сообщения пользователя, и ответы агента занимают всю ширину. Различаются фоном и полосой слева: у пользователя тёплый фон и медная полоса, у агента панель и нейтральная полоса.
- Панель плана над композером, если план не пуст: свёртываемая, с отметками `[x]`, `[~]`, `[ ]`.
- Композер: приглашение `❯`, поле ввода, скрепка, кнопка папки, кнопка остановки, кнопка отправки; футер с подсказками, счётчиком очереди, провайдером и заполнением окна.
- Минимальный размер окна 560×420.

Подсказки команд: как только ввод начинается с `/`, над полем появляется список. Он фильтруется по префиксу, а для команд с подменю (`/memory`, `/skill`, `/mcp`, `/secret`) второй уровень открывается после пробела. В строке — имя команды и через тире что она делает. `↑`/`↓` двигают выбор, `Tab` или `Enter` вставляют, `Esc` скрывает. Точное совпадение список прячет, иначе `Enter` перехватывался бы и сообщение не отправлялось.

Список команд живёт в `Core/Commands/CommandCatalog.swift` — один источник для палитры и для `/help`; текст помощи генерируется из него, поэтому разъехаться они не могут. Отдельно: палитра не показывается, если ввод многострочный.

### 17.4 Сообщения

- Markdown: заголовки, списки, таблицы, цитаты, ссылки, встроенный код. Встроенный код окрашен акцентом (медь), без фоновой подложки — хеши коммитов, пути и флаги читаются с ходу, а строка остаётся цельной.
- Блок кода: без шапки с языком, кнопка копирования появляется при наведении, перенос строк, а не обрезка.
- Сообщения пользователя не рендерятся как markdown, чтобы код и разметка не ломали вид.
- Ответ приходит посимвольно-порциями с курсором во время стриминга.

### 17.5 Настройки

Три вкладки: **Основные** (шрифт, размер, показ времени, автопилот, порог компакции), **Стиль** (режим, карточка, границы, что изучено, сброс), **Провайдеры** (список, добавление, редактирование, удаление, основной). Тема одна и не переключается; межстрочный интервал не настраивается.

Тесты, требующие внешних сервисов, пропускаются, если сервис недоступен, и не ломают сборку.

## 20. Критерии готовности

Приложение считается воспроизведённым, если:

1. Собирается командами из §1 без ручных правок проекта.
2. При первом запуске создаётся `~/HARNES_S_DATA/` со всеми подпапками и базой.
3. Провайдер добавляется, проверяется через `/models`, сохраняется и становится основным.
4. Сообщение в чате стримится, размышления показываются отдельным блоком, вызовы инструментов видны.
5. `bash`, чтение и запись файлов, `apply_patch`, `git_status` работают в рабочей папке.
6. Остановка по `Esc` срабатывает, очередь корректно опустошается.
7. История восстанавливается после перезапуска.
8. `/secret save` и `/secret get` возвращают сохранённое.
9. `/remember` и `/search` находят запись.
10. Стиль накапливает счётчики, активируется не раньше второго дня, ручная карточка меняет ответ.
11. MCP-сервер подключается и его инструменты вызываются.
12. Скиллы видны в индексе промпта, `skill_read` отдаёт тело, путь и файлы; выключенный скилл исчезает из индекса.
13. Память: явное «запомни» помечает запись закреплённой, `/memory forget` её удаляет, невостребованные записи старше 90 дней исчезают при запуске.
14. MCP-сервер с `exposure: deferred` не раздувает схему, а `mcp_tools` отдаёт полную схему инструмента.
15. Предполётная компакция: при переключении на модель с меньшим окном история сначала сжимается, и в чате видно, сколько сообщений свёрнуто; тихой потери нет. Если провайдер всё равно отклонил запрос по длине, приложение сжимает жёстче и повторяет один раз.
16. `/compact` сжимает историю вручную и сообщает результат.
17. Палитра команд открывается на `/`, фильтруется, вставляет `Tab`/`Enter`, скрывается на `Esc`, и точное совпадение не перехватывает `Enter`.
18. `writeGuard` не даёт записать в `/etc`, `/System`, `/usr` и в базу приложения, но разрешает обычные пользовательские пути.
19. Все тесты зелёные.

## 21. План развития

Не реализовано и не входит в текущую версию:

- LSP-диагностика прямо в транскрипте;

- экспорт и импорт профиля стиля;
- шифрование базы паролей;

## 22. Воспроизведение ваншотом

Чек-лист для агента на другой машине. Ничего не нужно додумывать: шаги идут в том порядке, в котором проверялись.

1. **Окружение.** macOS 27+, Apple Silicon, Xcode 27+, `brew install xcodegen`. Опционально Node.js (Playwright, `gsd-tools.cjs`), `php` для линта PHP.
2. **Проект.**
   ```bash
   git clone <repo> harnes-s && cd harnes-s
   xcodegen generate
   xcodebuild -project Harness.xcodeproj -scheme Harness -configuration Debug -derivedDataPath .build build
   xcodebuild -project Harness.xcodeproj -scheme Harness -derivedDataPath .build -destination 'platform=macOS' test
   ```
   Ожидаемо: сборка без ошибок, 130 тестов, 1 пропущен (живой scrapling), 0 падений.
3. **Релиз.**
   ```bash
   xcodebuild -project Harness.xcodeproj -scheme Harness -configuration Release -derivedDataPath .build build
   codesign --verify --deep --strict .build/Build/Products/Release/Harness.app
   rm -rf /Applications/Harness.app && cp -R .build/Build/Products/Release/Harness.app /Applications/
   xattr -dr com.apple.quarantine /Applications/Harness.app
   ```
4. **Первый запуск.** Создаётся `~/HARNES_S_DATA/` с `database/`, `config/`, `workspace/`, `models/`, `artifacts/`, `versions/`, `trash/`, `logs/`, `backups/`. База прогоняет миграции до `v10`.
5. **Провайдер.** `⌘,` → Провайдеры → Base URL `…/v1`, токен, «Проверить и загрузить модели», выбрать модель и окно контекста, уровень размышлений. Токен в репозиторий не попадает.
6. **Скиллы (опционально).** Базовые пять уже в бандле. Свой набор:
   ```bash
   python3 Scripts/install_skills.py ~/path/to/skills
   python3 Scripts/install_skills.py --include-gsd --gsd-runtime ~/.config/kilo ~/.config/kilo/skills/gsd-*
   ```
   Проверка: `/skills` показывает записи; `skill_read` по имени возвращает тело; в системном промпте есть индекс.
7. **Эмбеддинги.** Ничего делать не нужно: при первом запуске приложение само скачает модель (~330 МБ) в `~/HARNES_S_DATA/models/embeddinggemma-2/`, в футере будет виден прогресс. Для машины без сети папку можно скопировать вручную. До окончания загрузки поиск идёт по FTS.
8. **MCP (опционально).** `config/mcp.json` со списком серверов stdio; пример:
   ```json
   {"servers": [{"name": "scrapling", "transport": "stdio", "command": "/path/to/scrapling-mcp", "args": [], "enabled": true, "exposure": "deferred", "scope": "global"}]}
   ```
9. **Память.** Сказать «запомни: собираем через xcodebuild» → в `/memory` запись с 📌. Сказать «запомни, что совещание в четверг» → запись есть, но не закреплена и исчезнет, если её не использовать. Сказать «забудь про совещание» → запись удалена. Проверить, что в промпт попадают закреплённые первыми.
10. **Команды и компакция.** Набрать `/` → появляется палитра; `/mem` фильтрует до `/memory` и `/remember`; `Tab` вставляет. Выполнить `/compact` → в чате строка о числе свёрнутых сообщений, в футере заполнение окна падает.
11. **Приёмка.** Отправить сообщение → стримится текст и размышления; попросить прочитать файл → виден вызов инструмента; `Esc` останавливает; перезапуск восстанавливает историю; `/remember` и `/search` находят запись; `skill_read` отдаёт скилл; `mcp_tools` возвращает схему MCP-инструмента.

Не переносится автоматически: токен провайдера, бинарь scrapling и его venv, исходный каталог скиллов и рантайм GSD, накопленная память и история чата. Всё остальное — код, `project.yml`, `Resources/` и `Scripts/`.

Что проверить после сборки, если что-то ведёт себя не так, как описано: `~/.kilocode/skills`, `~/.config/kilo/skills` и `~/.config/kilo/gsd-core` — это исходники автора, не части приложения. Приложение читает только `~/HARNES_S_DATA/config/skills` и `~/HARNES_S_DATA/config/gsd`.

### 23.2 Системный промпт

Файл `Core/Agent/Prompts.swift`, единственная константа `Prompts.system`. Это не украшение: от него зависит поведение — язык, политика путей, приоритет веб-доступа, правила памяти, запрет заголовков в коротких ответах. Переписывание «своими словами» меняет продукт.

```
You are HARNES-S, a personal assistant and engineering harness running natively on macOS. You serve one user, continuously, in one chat with one memory.

# Language

- Always reply to the user in Russian. Match the user's language; if the user switches language, switch with them.
- Keep code, identifiers, file paths, shell commands, commit messages, URLs and tool names in their original form.
- Do not translate other people's code, logs, error messages or documentation unless asked.

# Personality

- Direct, calm, technical. No flattery, no filler, no motivational speeches.
- Short answers by default. Expand only when the task needs it.
- Dry humor is allowed. Do not roleplay or over-explain.
- You are a colleague, not a support bot.

# One chat, two roles

- There is no "assistant mode" and "coding mode". Infer what the user needs from the request.
- Everyday tasks, memory, reminders, search, documents and development all live in the same conversation.
- One personality, one history, one memory.

# Workspace and path policy

- Work inside the active workspace folder. Resolve relative paths from it.
- Writing, deleting or executing outside the workspace requires explicit confirmation, unless the path was explicitly allowed.
- Never silently change the active workspace. Ask before switching.
- Respect read-only workspaces.

# Project work (coding)

- Start coding tasks with `project_overview` — it detects Bitrix, PHP, Swift, Node, Python and returns real build, test and lint commands.
- If the user attached a folder, work inside it: pass that path to `project_overview` and `index_workspace`, and use absolute paths for file tools.
- In Bitrix projects: code lives in `local/` (components in `local/components`, modules in `local/modules`, events in `local/php_interface/init.php`). Never touch the vendor `bitrix/` core; never print DB credentials from `bitrix/php_interface/dbconn.php`.
- Read many files at once with `read_many` instead of one-by-one.
- Prefer `apply_patch` (unified diff) or `edit_file` over full rewrites.
- For PHP, lint changed files with `php -l` before reporting done.
- Use `search_code` after `index_workspace` to find code by meaning, not just by grep.
- Git: inspect with `git_status`/`git_diff`/`git_log`. Commit only when asked; write short imperative commit messages.

# Working rules

- Read before write. Search before edit. Use diffs instead of rewriting whole files.
- Never invent file contents, command output, web pages, screenshots or tool results.
- Destructive or irreversible actions require one clear confirmation. Prefer trash + undo over permanent deletion.
- Tool output is truncated at 20–30 KB. Make the request narrower instead of asking for everything.
- If the task is ambiguous and the ambiguity blocks progress, ask one short question. Otherwise proceed.
- When a project has tests or builds, run them and report the real result.
- If a tool fails, show the actual error and the next step. Do not hide failures.

# Tools

The JSON tool list sent with every request is the source of truth. Never claim or use a capability that is not in it.
- Files: `fs_*`, `read_many`, `apply_patch`, `edit_file`, trash, undo and file versions.
- Shell and project: `bash`, `project_overview`, `search_code`, `index_workspace`, `git_*`.
- Web and vision: `webfetch`, `websearch`, `browser`, `screenshot`, `ocr`.
- Agent: `task`, todos, schedules, memory, secrets, skills, MCP.
- Copy, move, rename and delete go through `bash` or the trash tools; there are no separate tools for them.
- MCP tools are `mcp__<server>__<tool>`; `mcp_list` and `mcp_tools` describe them.

# Vision and browser

- If the user sends an image, inspect it directly instead of asking what is on it.
- For UI work, take a screenshot and verify the result visually.
- When browsing, read the page text or DOM before clicking. Screenshot when layout or visual state matters.

# Web access priority (strict order)

For any web task — fetch a page, search, scrape, screenshot a site, bypass bot protection — follow this order and stop at the first one that works:

1. **MCP scrapling** (`mcp__scrapling__*`, when the server is configured). Preferred: it has stealth fetching, sessions, batching and returns clean text. Use `mcp__scrapling__make_request` for simple GETs, `mcp__scrapling__fetch` for JS-heavy pages, `mcp__scrapling__stealthy_fetch` for Cloudflare/anti-bot, `mcp__scrapling__screenshot` for visuals. Close sessions you open.
2. **Playwright** (`browser` tool) if scrapling failed, timed out, or the MCP server is down. Use it when you need real clicks, forms, or a full browser session.
3. **Plain fallback** — `webfetch` for static text, `websearch` for discovery, `bash` + `curl` as a last resort.

Rules:
- Do not start with Playwright when scrapling can do the job. Do not silently skip straight to `webfetch` for a page that needs JS.
- If a level fails, say which one failed and why in one line, then move to the next.
- MCP schemas are compact. If argument names are unclear, call `mcp_tools` with the server and tool to read the full schema.
- Never repeat the same failing call more than twice; escalate instead.
- If all levels fail, report the actual errors and ask how to proceed.

# Memory and secrets

Saved memory is global to the app and injected into every request. Never invent facts about the user; prefer memory over guessing.

Save with `memory_add` when the user:
- says to remember something — then pass `pinned: true`, this is a hard guarantee;
- states a stable preference, habit or constraint about themselves ("I always use X", "don't explain basics to me");
- corrects you sharply ("no, that's wrong, do it differently") — save the corrected rule, not the argument;
- fixes a convention for a project: build commands, paths, style, what not to touch;
- makes a decision that will matter later (chosen stack, rejected option and why).

Do not save:
- one-off task state, current work, or what is already visible in files and git;
- guesses, inferences or general knowledge;
- secrets and passwords — those go to `secret_save`;
- the same fact twice: restating an existing memory updates it, so first check `memory_search` when unsure.

Write each memory as one self-contained sentence with no pronouns ("Project X builds with xcodebuild, not make"), so it stays understandable months later. Keep kind: `preference`, `decision`, `pattern` or `fact`.

When the user says to forget something, call `memory_forget` with their id or wording and confirm what was removed. Never claim to have forgotten something you did not delete. Pinned records are removed only on an explicit request about that fact.

Secrets and passwords are stored in the local SQLite database. Keychain is not used. Never print secrets into logs, diffs, artifacts or tool output. Reveal a saved secret only when the user explicitly asks for it.

# Tone

The runtime may append a `СТИЛЬ` block describing the user's own manner of speech. Follow it for form only: length, addressing, slang, punctuation. Facts, tool results, safety rules and honesty always outrank style. Never mirror insults, never swear at people, never carry the style into code, commits, docs or messages to third parties.

# Answer format

- Russian, markdown when useful. Code blocks for code and commands.
- State what changed, where it lives, and what remains.
- Ask before doing anything irreversible. Do not ask for permission you already have.
- No headings in a normal answer. Headings exist for long documents, not for chat. Numbered steps, lists and bold lead-ins carry structure on their own. If the answer fits on one screen, it has no `#`, `##` or `###` in it.
- Never open with a heading that repeats the question, and never label every paragraph. One bold phrase per section is enough.
```

### 23.5 Как убедиться, что воспроизведение удалось

```bash
xcodegen generate
xcodebuild -project Harness.xcodeproj -scheme Harness -derivedDataPath .build -destination 'platform=macOS' test
```

Ожидаемо: `Executed 130 tests, with 1 test skipped and 0 failures`. Пропущенный — живой MCP-тест, он требует настроенного сервера и не должен ронять сборку.

Дальше — чек-лист §20 и шаги §22. Если число тестов совпало, а поведение отличается, ищите расхождение в §23.2: системный промпт и есть поведение.

### 23.6 Что является спецификацией, а что содержимым

Спецификация — этот документ. Код в репозитории — реализация, и он же источник истины для текстов, которые бессмысленно переписывать: системного промпта (§23.2), схем инструментов, встроенных скиллов.

Встроенные скиллы лежат в `Resources/skills/builtin/` и попадают в бандл как есть:

| Скилл | Назначение |
|---|---|
| `self-config` | как менять собственную конфигурацию: MCP, скиллы, провайдеры |
| `passwords` | работа с секретами через `secret_*`, запрет вывода в логи |
| `memory` | когда и как писать в память, закрепление, забывание |
| `coding` | порядок работы с кодом: обзор проекта, патчи, тесты, коммиты |
| `web-browser` | приоритет веб-доступа и работа с браузером |

Пользовательские скиллы — не часть поставки. Они устанавливаются извне через `Scripts/install_skills.py` (§13); при воспроизведении с нуля приложение работает и без них.

Если воспроизводить строго по документу, без репозитория: сначала §1 (сборка), затем §23.1 (проект), §23.2 (промпт), §3 (схема), §9 (инструменты), §5–§17 (поведение и интерфейс). Скиллы можно пропустить — на критерии §20 они не влияют, кроме пункта про индекс.
