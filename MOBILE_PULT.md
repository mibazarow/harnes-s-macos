# MOBILE_PULT — Android-пульт для HARNES-S через свой транспортный сервер

Документ описывает мобильную часть: **Android-приложение, которое является только пультом к
Mac-версии**, и **свой сервер-транспорт**, который сводит телефон и Mac вместе.

- Исходник: `macOS_AGENT_HARNESS` (Swift 6, SwiftUI, SQLite, SSE-клиент провайдера).
- Платформа телефона: **только Android**. iOS не планируется и в архитектуре не учитывается.
- Главный принцип: **сервер — это настройка, а не зависимость.** Нет настройки — нет сервера —
  приложение на Mac работает ровно как сейчас, без диалогов, задержек и упоминаний.

---

## 0. Коротко

```
┌──────────────┐        WSS         ┌───────────────────┐        WSS         ┌──────────────┐
│   Android    │ ─────────────────▶ │ Сервер-транспорт  │ ◀───────────────── │     Mac      │
│   (пульт)    │                    │  (перекладывает   │                    │   (агент)    │
│              │ ◀───────────────── │      байты)       │ ──────────────────▶ │              │
└──────────────┘                    └───────────────────┘                    └──────────────┘
```

1. На Mac в настройках появляется блок **«Телефон»**: адрес сервера, порт, логин, пароль.
2. На Android те же четыре поля.
3. Оба подключаются к серверу исходящим соединением и попадают в один «ящик».
4. Телефон видит тот же чат, что и Mac, и может отправлять сообщения и нажимать «стоп».
5. Удалил настройку сервера на Mac — всё, сервера нет. Приложение живёт как обычное настольное.

Телефон **не** вызывает инструменты, не читает файлы, не ходит в память напрямую. Он говорит в
тот же чат. Решение, что делать, принимает агент на Mac.

## 1. Из чего состоит

| Компонент | Где живёт | Что делает |
|---|---|---|
| **Сервер-транспорт** | VPS с белым адресом | сводит пару «Mac + телефон», пересылает кадры, ничего не разбирает |
| **Мост на Mac** | внутри приложения, `Services/RemoteTransport.swift` | держит соединение, отдаёт состояние, принимает команды, публикует события |
| **Android-приложение** | телефон | показывает транскрипт, отправляет текст, кеширует историю |
| **Настройка сервера** | Mac: `Настройки → Телефон`; Android: экран настроек | адрес, порт, логин, пароль |

Сервер не хранит переписку, не имеет базы, не знает, что внутри кадров. Он существует только
пока телефон хочет видеть Mac.

## 2. Настройка сервера на Mac

Новая вкладка в настройках: **«Телефон»**. Ничего не появляется, пока пользователь сам не
откроет её и не заполнит.

### 2.1 Поля

| Поле | Тип | По умолчанию | Правила |
|---|---|---|---|
| `Адрес сервера` | текст | пусто | домен или IP; без схемы, без слэша |
| `Порт` | число | `443` | 1–65535 |
| `Логин` | текст | пусто | 1–64 символа, без пробелов |
| `Пароль` | защищённое поле | пусто | 1–256 символов, показывается точками |
| `Использовать TLS` | переключатель | включён | выключение разрешено, но с предупреждением |
| `Требовать подтверждение нового устройства` | переключатель | выключен | см. §5.2 |

Поля проверяются на лету: пустой адрес, нечисловой порт, пробел в логине — кнопка
«Подключиться» неактивна и рядом с полем написано, что не так. Никаких модальных окон.

### 2.2 Кнопки

| Кнопка | Что делает |
|---|---|
| **Проверить связь** | подключается, проходит авторизацию, отключается, показывает задержку и версию сервера. Ничего не сохраняет |
| **Сохранить и подключиться** | пишет настройку, запускает соединение в фоне, закрывать вкладку можно сразу |
| **Отключиться** | закрывает соединение, настройку оставляет |
| **Удалить сервер** | стирает адрес, порт, логин, пароль, останавливает соединение, снимает все повторы |

### 2.3 Строка состояния

Одна строка под кнопками, без баннеров и всплывающих окон:

| Состояние | Текст | Цвет |
|---|---|---|
| настройки нет | `Сервер не настроен` | приглушённый |
| идёт подключение | `Подключение…` | приглушённый |
| на связи | `На связи · 12 мс` | акцент |
| сервер недоступен | `Сервер недоступен, повтор через 8 с` | приглушённый, не красный |
| неверный логин или пароль | `Неверный логин или пароль` | приглушённый |
| TLS-ошибка | `Сертификат сервера не принят` | приглушённый |

Важно: **ни одно из этих состояний не блокирует работу**. Агент, инструменты, память и чат в
окне работают независимо от того, что написано в этой строке.

### 2.4 Поведение при удалении

Кнопка «Удалить сервер»:

1. Закрывает WebSocket, если он открыт.
2. Стирает четыре поля и флаги из `app_state`.
3. Отменяет запланированные повторы (никаких фоновых попыток после удаления).
4. Убирает строку статуса из футера композера.
5. Ничего не пишет в чат.

После этого в приложении не остаётся ни одного следа сервера: ни таймера, ни задачи, ни
подключения. Следующий запуск тоже ничего не помнит.

### 2.5 Хранение

Пароль лежит в локальной SQLite в `app_state` под ключом `remote.password` — так же, как
секреты в приложении, без Keychain. Это осознанно: папка данных должна оставаться переносимой,
а сервер всё равно видит только то, что вы сами через него гоняете.

## 3. Android-приложение

### 3.1 Стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык | Kotlin 2.1 | стандарт для Android |
| UI | Jetpack Compose (Material 3) | быстрый и предсказуемый рендер, без XML |
| Сеть | OkHttp 5 (`WebSocketListener`) | надёжный WebSocket, реконнект руками |
| JSON | kotlinx.serialization | строгие модели, те же имена полей, что на Mac |
| Кеш | Room 2.7 | SQLite, как на Mac, те же колонки |
| Настройки | DataStore (Preferences) | простые пары ключ-значение |
| Пароль | `androidx.security:security-crypto` (EncryptedSharedPreferences) | ключ в Android Keystore |
| Фон | Foreground Service типа `dataSync` | удержать соединение при активном чате |
| Уведомления | NotificationCompat + канал «Ответ готов» | сообщить о завершении длинной задачи |
| Markdown | `com.mikepenz:multiplatform-markdown-renderer` | готовый Compose-рендер |
| Сборка | Gradle 8.7, AGP 8.6 | обычный стек |

`minSdk 26` (Android 8.0), `targetSdk 35`. Ниже 26 не нужно: там нет нормального фонового
сервиса и Keystore.

### 3.2 Экраны

Приложение состоит из трёх экранов и не пытается быть больше.

**1. Чат** — главный и единственный рабочий.

```
┌───────────────────────────────────┐
│ HARNES-S        ● на связи   ⋮    │   шапка: статус, меню
├───────────────────────────────────┤
│                                   │
│   вы · 14:02                      │
│   Открой проект и найди, где      │
│   проверяется авторизация         │
│                                   │
│   HARNES-S · 14:02                │
│   > размышления · 214 симв.       │
│   ├ fs_read  Core/Auth.swift      │
│   ├ search_code  "authorize"      │
│   Точка входа — ...               │
│                                   │
│              [ ↓ в конец ]        │
├───────────────────────────────────┤
│ [ 📎 ] Написать…            [ ▶ ] │   композер
└───────────────────────────────────┘
```

- Транскрипт: те же роли, те же трассы инструментов, те же свёрнутые размышления.
- Пользовательские сообщения — слева с медной полосой, ответы — с серой (как на Mac).
- Встроенный код — медным, без фона.
- Автоскролл прилипает к низу, если пользователь у низа.
- Кнопка отправки превращается в «стоп» во время стрима.
- В шапке — точка состояния: `на связи` / `переподключение` / `Mac недоступен`.

**2. Настройки сервера** — те же четыре поля, что на Mac.

| Поле | Подсказка |
|---|---|
| Адрес | `relay.example.com` |
| Порт | `443` |
| Логин | `mb` |
| Пароль | скрытый, с кнопкой «показать» |

Кнопки: «Проверить», «Подключиться», «Отключиться», «Забыть сервер». Строка состояния — как на
Mac.

**3. О приложении** — версия, версия протокола, кнопка «Очистить кеш».

### 3.3 Локальный кеш

Телефон должен читаться без сети — в метро, в самолёте.

```kotlin
@Entity(tableName = "messages")
data class CachedMessage(
    @PrimaryKey val serverId: Long,   // id сообщения с Mac
    val role: String,                 // user | assistant
    val text: String,
    val reasoning: String?,
    val toolsJson: String,            // сериализованный список трасс
    val createdAt: String,
    val seq: Long                     // порядковый номер события
)

@Entity(tableName = "pending")
data class PendingMessage(
    @PrimaryKey val clientId: String, // UUID, придуманный телефоном
    val text: String,
    val attachmentsJson: String,
    val createdAt: String
)
```

- Кеш хранит последние 500 сообщений; старше — удаляются при вставке.
- При старте: сначала показываем кеш, потом подключаемся и догружаем недостающее.
- Кеш — только для чтения. Источник истины всегда Mac.

### 3.4 Очередь отправки

Телефон может быть без сети. Сообщение не теряется:

1. Пишется в `pending` с `clientId` (UUID).
2. Показывается в транскрипте с пометкой «в очереди».
3. При подключении отправляется. Mac отвечает `ack {clientId}`, после чего строка уходит из
   `pending` и заменяется настоящим сообщением с серверным `id`.
4. Повторная отправка того же `clientId` Mac отбрасывает — двойного сообщения не будет.

### 3.5 Фон и ограничения Android

Честно о том, что мешает:

- **Экран погас → система может придушить сокет.** Лечится Foreground Service с типом
  `dataSync` и постоянным уведомлением «HARNES-S на связи» — но только пока сервис запущен,
  то есть пока пользователь в чате.
- **Doze и App Standby** режут сеть в фоне. Поэтому основной сценарий: приложение на экране.
  Фоновые уведомления — только о завершении задачи.
- **Пуш-уведомлений без Firebase нет.** Вариант: Mac шлёт уведомление через сам сервер
  (сервер держит лёгкое соединение и отправляет `notify`), телефон показывает локальное
  уведомление. Это работает, пока сервер жив, и не требует Google-сервисов.
- **Батарея.** Реконнект с нарастающей паузой (1 → 2 → 4 → … → 60 с), а не раз в секунду.

### 3.6 Уведомление о готовом ответе

Пока пользователь в приложении — не нужно, он видит стрим. Нужно, когда экран погас:

1. Mac завершил ответ, отправил `done`.
2. Сервер видит, что телефон отключён, и держит событие в буфере 5 минут.
3. Телефон при следующем подключении видит пропущенное и показывает локальное уведомление
   «HARNES-S закончил ответ».

Без Firebase, без Google-аккаунта, без серверной инфраструктуры уведомлений.

## 4. Протокол

### 4.1 Транспорт

WebSocket поверх TLS. Оба конца подключаются **исходящим** соединением — никаких портов на Mac
и на телефоне, никакого проброса на роутере.

```
Mac     ──▶ wss://<адрес>:<порт>/v1/session
Android ──▶ wss://<адрес>:<порт>/v1/session
```

TLS обязателен. Сертификат — Let's Encrypt, выпускается автоматически (Caddy или встроенный
ACME-клиент сервера). Если пользователь выключил TLS, приложение предупреждает, что трафик
пойдёт открытым текстом, но не запрещает: это его сервер.

### 4.2 Авторизация

Первый кадр после подключения — `auth`:

```json
{"t":"auth","login":"mb","password":"…","role":"mac","device":"MacBook Pro 16","proto":1}
```

Ответ сервера:

```json
{"t":"auth_ok","mailbox":"mb","session":"<token>","proto":1,"server":"harnes-relay 1.0"}
```

или

```json
{"t":"auth_fail","reason":"bad_credentials"}
{"t":"auth_fail","reason":"rate_limited","retry_after":30}
```

- Пароль на сервере хранится как Argon2id-хеш. Открытого текста нет нигде.
- `mailbox` = логин. Mac и телефон с одним логином попадают в один ящик.
- `session` — токен для переподключения без повторной отправки пароля; живёт 30 дней.
- Ограничение частоты: 10 попыток в минуту на IP, дальше `rate_limited`.

Один логин = один Mac. Если подключится второй Mac с тем же логином, сервер отклонит его с
`mac_already_connected` — так пользователь не получит два агента, спорящих за один чат.

### 4.3 Кадры

Два вида:

- **текстовые** — JSON-события, читаемые глазами при отладке;
- **бинарные** — вложения (картинки), чтобы не раздувать base64.

Правило сервера: **не разбирать текстовые кадры**. Он смотрит только на `t` в первом кадре
(`auth`), дальше пересылает всё как есть второму участнику ящика.

### 4.4 События Mac → телефон

```json
{"t":"state","seq":101,"streaming":true,"model":"deepseek-v4.1",
 "context":{"used":41200,"limit":80000},"queued":0}

{"t":"message_start","seq":102,"id":4711,"role":"assistant","created":"2026-11-07T09:10:00Z"}
{"t":"delta","seq":103,"id":4711,"text":"Смотрю файл…"}
{"t":"tool_trace","seq":104,"id":4711,"name":"fs_read","summary":"Core/Auth.swift · 1–120","running":true}
{"t":"tool_trace","seq":105,"id":4711,"name":"fs_read","summary":"Core/Auth.swift · 1–120","running":false,"error":false}
{"t":"reasoning","seq":106,"id":4711,"text":"Сначала найду точку входа"}
{"t":"message_end","seq":107,"id":4711}
{"t":"done","seq":108}

{"t":"ack","seq":109,"clientId":"6f1c…","id":4712}
{"t":"warning","seq":110,"id":4711,"text":"Последний инструмент вернул ошибку…"}
{"t":"error","seq":111,"message":"Провайдер отклонил запрос"}
```

Каждое событие несёт `seq` — монотонный номер в рамках ящика. Он же — ключ восстановления после
обрыва.

### 4.5 Команды телефон → Mac

```json
{"t":"send","clientId":"6f1c…","text":"Открой проект","attachments":[]}
{"t":"stop"}
{"t":"history","before":4600,"limit":200}
{"t":"state"}
{"t":"resume","seq":98}
```

Телефон не может попросить «выполни команду», «прочитай файл» или «вызови инструмент». Такого
типа в протоколе нет. Максимум — текст в тот же чат, что и с клавиатуры Mac.

### 4.6 Восстановление после обрыва

1. Телефон помнит последний `seq`.
2. При подключении отправляет `resume {seq}`.
3. Сервер отдаёт всё из буфера, что новее (буфер — последние 5 минут, до 1 МБ на ящик).
4. Если буфер уже истёк, сервер отвечает `resume_failed`; телефон запрашивает `state` и
   `history {before: <последний известный id>}`.
5. Транскрипт в любом случае полный: он хранится на Mac, телефон только отображает.

## 5. Допуск устройства

### 5.1 Базовый режим (по умолчанию)

Логин и пароль — единственное, что нужно. Кто знает пароль, тот видит чат. Это простой и
понятный режим: свой сервер, свой пароль.

При первом подключении Mac показывает в чате системную строку:
`Подключён телефон «Pixel 8», 07.11 09:14`. Не диалог, не запрос — просто уведомление, чтобы
пользователь заметил чужое устройство.

### 5.2 Строгий режим (переключатель)

Если включён «Требовать подтверждение нового устройства»:

1. Телефон подключается, Mac получает `device_request` с именем и моделью.
2. В чате появляется вопрос с двумя кнопками: «Разрешить» / «Отклонить».
3. До ответа телефон видит «Ожидает подтверждения на Mac» и не получает историю.
4. Разрешённые устройства запоминаются по `deviceId` (генерируется на телефоне, хранится в
   Keystore) и больше не спрашивают.
5. В настройках Mac — список устройств: имя, последнее подключение, «Отозвать».

Отзыв рвёт соединение немедленно и запрещает повторный вход этому `deviceId`, даже с верным
паролем.

### 5.3 Что защищает пароль, а что нет

| Угроза | Ответ |
|---|---|
| Пароль утёк | TLS + смена пароля на сервере; при строгом режиме — ещё и отзыв устройства |
| Подбор пароля | Argon2id + ограничение частоты |
| Чужой VPS | сервер видит переписку — поэтому он ваш; логирование содержимого отключено |
| Кража телефона | пароль в Keystore, строгий режим, отзыв с Mac |
| Чужое устройство в сети | без логина не подключится; при строгом режиме — ещё и подтверждение |

Честно: при логине и пароле сервер **может** прочитать трафик, потому что TLS заканчивается на
нём. Это принято осознанно ради простоты. Если понадобится — есть отдельный раздел §9 про
сквозное шифрование, которое включается позже без смены протокола.

## 6. Бесшовность

### 6.1 Общие правила

- Сервер не входит в критический путь приложения на Mac.
- Ни одна операция в окне не ждёт сервер.
- Таймаут подключения — 5 секунд, дальше только фон.
- Все повторы — с нарастающей паузой и джиттером: 1, 2, 4, 8, 16, 32, 60, 60… секунд.

### 6.2 Телефон ушёл в фон

Экран погас, соединение упало. Это норма.

- Последний `seq` сохранён.
- Вернулся — `resume`, догон из буфера.
- Буфер истёк — `state` + `history`, транскрипт восстанавливается с Mac.

### 6.3 Mac заснул

- Телефон показывает «Mac недоступен», но **не** «ошибка».
- Кеш читается, история на месте.
- Отправленное копится в `pending` и уходит после пробуждения.
- Дубликатов нет: `clientId` дедуплицируется на Mac.

### 6.4 Сервер упал

**На Mac:** ничего. Соединение переподключается в фоне, строка статуса меняется на «Сервер
недоступен, повтор через N с». Агент, инструменты, память, окно — работают.

**На телефоне:** «Нет связи», кеш читается, сообщения в очереди.

**Сервер вернулся:** оба переподключаются сами, телефон догоняет, очередь уходит. Без
перезапуска приложений.

### 6.5 Сервер удалён

Пользователь нажал «Удалить сервер»:

- соединение закрыто;
- повторы отменены;
- настройка стёрта;
- строка статуса исчезла;
- приложение ведёт себя как до появления этой функции.

Телефон при этом показывает «Сервер не настроен» и работает с кешем.

### 6.6 Сменился адрес или пароль

Пользователь правит поля на Mac, нажимает «Сохранить и подключиться». Mac переподключается к
новому адресу. Телефону нужно ввести те же данные один раз — либо, если адрес не менялся, он
переподключится сам после смены пароля на сервере.

## 7. Сервер

### 7.1 Обязанности

| Что | Детали |
|---|---|
| Авторизация | Argon2id, токен сессии 30 дней, лимит попыток |
| Сведение пары | по `mailbox` = логин; один Mac, до 5 телефонов |
| Пересылка | все кадры второго участника — как есть |
| Буфер | последние 5 минут или 1 МБ на ящик, в памяти |
| Keepalive | ping каждые 30 с, разрыв после трёх пропусков |
| Лимиты | кадр ≤ 4 МБ, 100 ящиков на процесс, 10 попыток входа в минуту на IP |
| Логи | только коды: `connect`, `auth_ok`, `auth_fail`, `drop`; без содержимого |

### 7.2 Чего сервер не делает

- Не пишет содержимое кадров на диск.
- Не хранит переписку.
- Не знает, где сообщение, а где картинка.
- Не участвует в работе инструментов и памяти.
- Не нужен для запуска Mac-приложения.

### 7.3 Конфигурация

`/etc/harnes-relay/config.yaml`:

```yaml
listen: ":443"
domain: "relay.example.com"
tls:
  mode: acme                 # acme | files
  cache: /var/lib/harnes-relay/acme
limits:
  frame_bytes: 4194304
  mailboxes: 100
  logins_per_minute: 10
  buffer_seconds: 300
  buffer_bytes: 1048576
users:
  - login: "mb"
    password_hash: "$argon2id$v=19$m=65536,t=3,p=4$…"
```

Добавление пользователя:

```bash
harnes-relay user add mb      # спросит пароль, допишет хеш в конфиг
harnes-relay user passwd mb   # смена пароля
harnes-relay user remove mb
```

### 7.4 Установка

```bash
# Ubuntu 24.04
scp harnes-relay-linux-amd64 root@server:/usr/local/bin/harnes-relay
ssh root@server 'chmod +x /usr/local/bin/harnes-relay && harnes-relay user add mb'
```

`/etc/systemd/system/harnes-relay.service`:

```ini
[Unit]
Description=HARNES relay
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=/usr/local/bin/harnes-relay --config /etc/harnes-relay/config.yaml
Restart=always
RestartSec=3
DynamicUser=yes
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ProtectHome=yes

[Install]
WantedBy=multi-user.target
```

### 7.5 Ресурсы и цена

| Параметр | Значение |
|---|---|
| CPU | 1 vCPU, десятки Mac |
| RAM | 128–256 МБ (всё состояние — буферы в памяти) |
| Диск | 10 ГБ: ОС и бинарник |
| Трафик | текст — килобайты; картинки ограничены 4 МБ |
| Цена | 3–5 $/мес + домен ~10 $/год |
| Перезапуск | безопасен: состояние пересоздаётся, клиенты переподключаются |

## 8. Реализация на Mac

### 8.1 Новый модуль

`Services/RemoteTransport.swift` — актор, ничего не знающий про UI.

```swift
actor RemoteTransport {
    enum State: Equatable {
        case unconfigured
        case connecting
        case online(latencyMS: Int)
        case retrying(nextIn: TimeInterval, reason: String)
        case failed(String)
    }

    private(set) var state: State = .unconfigured
    private var task: Task<Void, Never>?

    func configure(_ settings: RemoteSettings?)   // nil = удалить сервер
    func start()
    func stop()
    func publish(_ event: RemoteEvent)            // вызывается из ChatStore
    func send(_ command: RemoteCommand) async
}
```

### 8.2 Точки подключения

| Что | Где |
|---|---|
| Отправка текста с телефона | `ChatStore.send(text:attachments:)` — тот же вход, что у композера |
| Стоп | `ChatStore.stop()` |
| История | `ChatHistoryService.older(than:limit:)` |
| Состояние | `ChatStore.isStreaming`, `messages.last`, план контекста |
| События | подписка на изменения `ChatStore.messages` (наблюдение через `@Observable`) |

Ни одного нового пути в логике агента. Транспорт — сбоку.

### 8.3 Публикация событий

`ChatStore` уже меняет `messages` на каждом токене. Нужен один наблюдатель, который превращает
изменение в `delta`. Чтобы не гонять по сети каждый токен:

- события копятся и отправляются пачкой раз в 50 мс;
- `tool_trace` и `message_end` уходят сразу;
- при отсутствии телефона публикация — no-op, ноль стоимости.

### 8.4 Настройка

`app_state`:

| Ключ | Значение |
|---|---|
| `remote.host` | адрес |
| `remote.port` | порт |
| `remote.login` | логин |
| `remote.password` | пароль |
| `remote.tls` | `0` / `1` |
| `remote.strictDevices` | `0` / `1` |
| `remote.devices` | JSON-список разрешённых устройств |

`RemoteTransport.configure(nil)` при удалении стирает все ключи и останавливает задачу.

## 9. Сквозное шифрование (необязательный этап)

Нужно, если не хочется, чтобы сервер видел текст. Включается переключателем на Mac и телефоном
без смены протокола: меняется только содержимое кадров.

- Рукопожатие X25519, схема Noise XX, `CryptoKit` на Mac и `Tink`/`BouncyCastle` на Android.
- У Mac постоянный ключ; его отпечаток (8 групп по 4 hex-символа) показывается в настройках и
  сверяется на телефоне при первом подключении.
- Внутри кадра — `[версия][счётчик][nonce][шифротекст+тег]`, ChaCha20-Poly1305.
- Сервер после включения не может прочитать даже тип события.

Это отдельный этап после того, как всё работает. В первой версии его нет.

## 11. Риски

| Риск | Вероятность | Что делать |
|---|---|---|
| Android душит сокет в фоне | высокая | Foreground Service, реконнект, кеш; основной сценарий — экран включён |
| Сервер стал точкой отказа | низкая | он вне критического пути; тест «выключи сервер» в приёмке |
| Расхождение состояний | средняя | единственный источник истины — Mac; телефон только отображает |
| Большая картинка не проходит | средняя | сжатие на телефоне, лимит 4 МБ, понятный отказ |
| Домен и сертификат | низкая | ACME автоматически |
| Пароль в открытом виде на Mac | известная | так же, как остальные секреты приложения; папка данных переносимая |
| Два Mac на одном логине | низкая | сервер отклоняет второго с `mac_already_connected` |

## 12. Чек-лист приёмки

1. Сервер не настроен → Mac работает как обычно, ни одного упоминания сервера в интерфейсе.
2. Заполнил четыре поля → «На связи», телефон подключился, видит тот же чат.
3. Отправил с телефона → ответ стримится на обоих экранах одновременно.
4. Заблокировал телефон на 10 минут → вернулся, текст на месте, без дыр.
5. Mac уснул → телефон показывает кеш и «Mac недоступен», отправленное уходит после пробуждения.
6. Сервер упал во время ответа → Mac дописывает ответ, телефон догоняет после восстановления.
7. Сервер перезапущен с нуля → оба переподключились сами, без действий пользователя.
8. Удалил сервер на Mac → соединение закрыто, повторов нет, приложение как раньше.
9. Неверный пароль → «Неверный логин или пароль», Mac работает.
10. Строгий режим: новое устройство ждёт подтверждения; отзыв рвёт сессию немедленно.
11. На VPS нет ни байта переписки — проверить `strings` по диску и логи.

## 13. Чего в этой версии нет

- iOS. Только Android.
- Синхронизации памяти, секретов и настроек на телефон. Только транскрипт.
- Работы агента на телефоне. Телефон — пульт, не второй агент.
- Локального режима без сервера. Нет сервера — нет телефона, Mac работает как обычно.
- Веб-версии и PWA.
- Мультиаккаунта: один логин — один Mac.
